OVERVIEW

This artifact will demonstrate

  1. A knowledge graph made the smallest model as accurate as the biggest: Haiku went from a wrong answer to the right one, with zero tool calls and 2 ms retrieval.
  2. Faster and cheaper, measured: 20 seconds of visible searching became an instant answer; 660 to 1,180 tokens of document reads became ~400 tokens, fixed at any corpus size.
  3. Proven on a deliberate multi-hop trap case.
  4. The mechanism: deterministic prompt injection through a UserPromptSubmit hook, so retrieval bypasses the model entirely; the traversal is done before the model wakes.
  5. How to build your own: the ontology and logical modelling are covered below, and the repo teaches your AI the whole design system.

01 · THE TEST CASE

A trap, on purpose

What it proves: with a graph, even the smallest model answers a question that defeats keyword search.

  1. The rule lives in one file: refunds over £500 need the Ops Manager.
  2. The person lives in another: the Ops Manager is Sarah.
  3. The twist lives in a third: Sarah is away all March; Marcus covers her.
  4. Decoys are planted around them: a stale policy with different numbers, and an expenses document using the same £500.

The three files share no words, so keyword search finds the wrong things first. The artifact uses the same question against two folders — one raw, one with the graph — across three model sizes, with and without the graph.

“A customer wants an £800 refund in March. Who signs it off?”
Correct answer: Marcus Webb.
02 · THE DIFFERENCE

Pull vs push

The “pretend knowledge graph” pattern still makes the model search and read itself; the graph is decoration. Done properly, code finds the facts before the model is involved and hands them over. The model never takes part in finding them.

Pull · search during the turn

prompt→model→grep→read→grep→model→answer

seconds · cost grows with corpus size · accuracy depends on the model

Push · retrieve before the turn

prompt→hook queries graph
2 ms · no LLM→inject→model→answer

one model call · fixed cost · accuracy from structure

Artifact summary: Pull means the model hunts for facts during the conversation. Push means code finds the facts first and hands them over. That swap is the whole difference.

04 · RESULTS, CONTINUED

What happens as chains get longer

In the artifact, the dots are measured at the 3-hop chain. The curves are presented as the mechanism’s shape: each search hop adds calls, reads and a vocabulary guess; the graph walk is one query at any depth. The graph caveat is explicit: past top-k depth, ranking needs tuning.

Limits, and what fixes each

LimitWhen you feel itFixNature
Lexical seedingA question that names no known entity or alias finds nothing.Add embedding seeding beside the alias table.Extension, same design.
Top-k crowdingDense hub entities push chain links out of a fixed-size injection.Rank by path membership between seeds; prune; raise k.Tuning, same design.
Store sizePast a few hundred thousand edges, or heavy concurrent queries.Move up a tier. Same schema shape.Tier move.
Meaning at scaleName collisions merge; stale docs pollute.Disambiguation at extraction; supersession at ingest.Modelling discipline.
The limit is never hops. Six hops is six edges. Density, size, vagueness and ambiguity are the real axes, and nothing dead-ends.
05 · BUILD: THE ONTOLOGY AND THE LOGICAL MODEL

How to build an ontology

Start from the questions you want answered. List the kinds of things those questions mention; that becomes the entity vocabulary. List the ways those things connect; that becomes the relationship vocabulary. Keep both lists small and closed, and put conditions such as amounts, dates and windows in entity descriptions. The logical model is the shape a fact takes: a typed entity, a typed relation between two entities, and an alias for a name variant.

For the company-operations use case in the artifact, the questions were about approvals, roles and cover. Five entity types and five relationships followed from those questions. The extraction step then processes each document against that vocabulary.

Entity types

PERSON · ROLE · POLICY · PROCESS · DOCUMENT

Relationship types

approved_by · held_by · delegates_to · part_of · references

corpus/refund-policy.md

---
type: policy
title: Refund approvals
entities: [Refund approvals, Ops Manager]
links: [org-chart, customer-support-sop]
---
Refunds over £500 require approval by the **Ops Manager**
before payment is released.

Extraction also works on unstructured prose. The vocabulary is the prerequisite; front matter is maintenance discipline.

06 · BUILD: THE STORE

As many tables as your facts have shapes

The artifact’s logical-modelling rule is: list the shapes your facts take, and each shape becomes a table. This model uses three: a thing exists (entities), two things connect (relations), and a thing has another name (aliases). Three is not a magic number; facts in other shapes, such as time-bounded facts or measurements, imply additional tables.

src/schema.sql

CREATE TABLE entities (
  id TEXT PRIMARY KEY,              -- uuid5(type + normalised name)
  name TEXT,
  type TEXT,
  description TEXT,
  source_doc TEXT
);

CREATE TABLE relations (
  source_id TEXT,
  target_id TEXT,
  predicate TEXT,
  source_doc TEXT
);

CREATE TABLE aliases (
  entity_id TEXT,
  alias TEXT
);

Identity is computed, never looked up. An entity ID is derived from its type and normalised name, so repeated occurrences of “Ops Manager” across documents converge on the same node under that identity rule.

src/build_graph.py

def entity_id(type_: str, name: str) -> str:
    key = f"{type_}:{normalise(name)}"
    return str(uuid.uuid5(uuid.NAMESPACE_OID, key))
Artifact run: python src/build_graph.py → 13 entities, 13 relations, 10 aliases from 8 docs. Extraction varies run to run; deterministic IDs make re-runs merge instead of duplicating.
07 · BUILD: TRAVERSAL

Two jobs: find the starting points, walk the connections

Every implementation needs these two jobs, whatever the tier:

  1. Seeding: match question words against entity names and aliases.
  2. Walking: collect connected facts hop by hop.
Refund approvals
POLICY-- approved_by →Ops Manager
ROLE-- held_by →Sarah Chen
PERSON-- delegates_to (March) →Marcus Webb
PERSON

The question seeds at “refund”. The walk does the rest.

src/recall.py · recursive walk

WITH RECURSIVE walk(entity_id, depth) AS (
  SELECT id, 0 FROM entities WHERE id IN ({seeds})
  UNION
  SELECT CASE WHEN r.source_id = w.entity_id
              THEN r.target_id ELSE r.source_id END,
         w.depth + 1
  FROM relations r JOIN walk w
    ON w.entity_id IN (r.source_id, r.target_id)
  WHERE w.depth < ?
)
SELECT e1.name, r.predicate, e2.name, r.source_doc
FROM relations r
JOIN entities e1 ON e1.id = r.source_id
JOIN entities e2 ON e2.id = r.target_id
WHERE r.source_id IN (SELECT entity_id FROM walk)
  AND r.target_id IN (SELECT entity_id FROM walk);

08 · BUILD: INJECTION

The whole integration is one JSON field

hooks.json → .claude/settings.json

{
  "hooks": {
    "UserPromptSubmit": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "python src/recall_hook.py",
            "timeout": 10
          }
        ]
      }
    ]
  }
}

src/recall_hook.py

import json
import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parent))
from recall import recall

prompt = json.load(sys.stdin).get("prompt", "")
facts = recall(prompt, hops=3, top_k=8)
text = facts.as_text()

print(json.dumps({
    "systemMessage": text.split("\n")[0],
    "hookSpecificOutput": {
        "hookEventName": "UserPromptSubmit",
        "additionalContext": text,
    }
}))

additionalContext places the facts in front of the model before it thinks. systemMessage prints the count line at submit, before the model speaks.

The source says the hook fires on every prompt in this project only. A prompt matching nothing costs about a millisecond and one “no memory matches” line; a match costs at most top-k facts (~400 tokens). It explicitly names a relevance gate as the at-scale refinement.

09 · MAKE IT YOURS

Clone, swap, rebuild

graph-memory-starter/
├── corpus/                  8 modelled docs
├── corpus-before/           12 unstructured docs (the A/B control)
├── extraction/              LLM output per doc: nodes, edges, aliases
├── src/                     schema.sql, build_graph.py, recall.py, recall_hook.py
├── hooks.json
└── extract-prompt.md        the extraction prompt, for your own docs
  • Swap corpus/ for your docs.
  • Define your vocabulary from your questions.
  • Extract with extract-prompt.md.
  • Rebuild.

Needs: a coding assistant with prompt hooks, Python and SQLite. The source says nothing to install and no API key.

To reproduce the A/B exactly, the artifact says to run the search condition in corpus-before/ before wiring the hook (or isolate that folder so the hook never reaches it), and pin the same model on both sides with thinking off via "model" and MAX_THINKING_TOKENS=0.

APPENDIX

The full loop

READ PATH

user hits enter
↓
hook · recall_hook.py
↔ store · SQLite entities / relations / aliases
↓
model call · context pre-loaded

READ: deterministic, milliseconds
⇄
WRITE / COMPREHENSION PATH

turns + tool calls
↓
captured async, never blocks
↓
extract · LLM, deferred: idle / threshold
↓
writes triples to store

WRITE: expensive, when nobody waits
Capture is cheap and constant. Comprehension is expensive and deferred.
