## **Abstract** 

Recent advances in large language models (LLMs) have significantly improved automated code generation. While existing approaches have achieved strong performance at the function and file levels, real-world software engineering requires reasoning over entire repositories, including cross-file dependencies, evolving execution environments, and global semantic consistency. This challenge has led to the emergence of Repository-Level Code Generation (RLCG), where models must retrieve, organize, and utilize repository-scale context to generate coherent and executable code changes. To address these challenges, Retrieval-Augmented Generation (RAG) has become an increasingly important paradigm for repository-level code intelligence. In this survey, we present a comprehensive review of Retrieval-Augmented Code Generation (RACG), with a particular focus on repository-level approaches. Rather than viewing RACG as a static “retrieve-then-generate” pipeline, we characterize it as a coupled and evolving process involving context construction, retrieval optimization, generation, and environment interaction. We organize existing methods through a unified analytical framework spanning retrieval substrate, control regime, and evaluation setting. Based on this framework, we systematically examine retrieval strategies, graph-based and non-graph-based retrieval paradigms, training-driven optimizations, and autonomous agent architectures. We further summarize widely used datasets, benchmarks, and system configurations, and discuss key challenges including scalability, reliability, efficiency, and the necessity boundary between RACG and long-context LLMs. Through this survey, we aim to provide a structured understanding of the rapidly evolving RACG landscape and highlight promising directions for future AI-powered software engineering research.

## **1 Introduction** 

"If, as we confront some task, a part of the world functions as a process which, were it done in the head, we would have no hesitation in recognizing as part of the cognitive process, then that part of the world is part of the cognitive process." [Clark and Chalmers, 1998] 

Recent advances in large language models (LLMs) are transforming software development from code suggestion to broader software engineering capabilities [Jimenez et al., 2024]. Despite the inherent complexity of real-world development, characterized by large codebases, cross-file dependencies, and diverse tooling, agentic systems such as OpenClaw<sup>1</sup> , Claude Code<sup>2</sup> and Codex<sup>3</sup> demonstrate that LLMs can operate effectively in these environments and make progress. These advances mark a shift from isolated code generation to more integrated and practical software engineering workflows, as shown in Figure 1. In practice, development is repository-centric, where functionality arises from interactions across files. Consequently, models must not only produce locally correct code, but also maintain global consistency and adapt to an evolving execution environment. These requirements define the core challenges of modern code generation. 

**Challenges.** The first challenge is _long-range dependency modeling_ : critical information is distributed across files, documents, and dependencies, while changes in one file may affect distant modules, making it difficult to identify minimal but sufficient context and maintain cross-file consistency [Assogba and Ren, 2025]. The second is the _efficiency– correctness trade-off_ : issue resolution prioritizes accuracy, whereas real-time completion demands low latency. This trade-off is further complicated by model limitations—strong models may memorize common libraries, while weaker ones suffer from context overload [Wang et al., 2025g]. Scaling model size or context length only partially alleviates these issues and is often impractical for local deployment. Finally, _practical constraints_ further limit applicability: privacy and compliance restrict cloud-based use of proprietary code [Chen et al., 2025b, God of Prompt, 2025], and most LLMs are trained in outdated public repositories [Otterly.AI Blog, 2024], reducing adaptability in real-world and enterprise settings. 

The above challenges indicate that, in real-world settings, code generation is no longer a simple problem, but a complex process involving context selection and external information acquisition. In this context, Retrieval-Augmented Generation (RAG) offers an effective way to address context limitations by dynamically incorporating external knowledge during reasoning. In the code domain, this paradigm has evolved into **<u>Retrieval-Augmented Code Generation (RACG)</u>** , which enhances generation quality by retrieving relevant code and structural information. 

However, in repository-level scenarios, RACG is no longer a simple two-stage “retrieve-then-generate” pipeline. Instead, it becomes a dynamic process that can be coupled with customized indexing and structure-aware retrieval. We characterize RACG as a unified process in which the model (i) constructs and retrieves context from large-scale code repositories, and (ii) generates or modifies code based on the retrieved information and current system state. In addition to this core process, various enhancements—such as iterative refinement, multi-source context acquisition, and tool-assisted reasoning—can be incorporated to improve performance [Ma et al., 2025c, Su et al., 2024, Zhang et al., 2023a]. This formulation naturally aligns with **<u>Repository-Level Code Generation (RLCG)</u>** , which represents a new and challenging problem. 

Existing surveys have reviewed general RAG systems [Fan et al., 2024, Gao et al., 2024b], LLM-based code generation [Dong et al., 2025c, Jiang et al., 2025a], and code generation agents for software engineering [He et al., 2025]. However, these works do not systematically examine how retrieval is used to construct, select, and integrate the repository-level context. This survey fills this gap by providing a systematic overview of Retrieval-Augmented Code Generation in repository-level scenarios, organized around three questions: (i) how RACG methods are designed; (ii) how they are formulated and evaluated; and (iii) concerns and necessity boundary. Table 1 summarizes the positioning of this survey relative to previous work.

## **2 Preliminary and Methodological Foundations** 

This section formalizes the key concepts underlying Retrieval-Augmented Code Generation in repository-level settings. We focus on minimal yet sufficient abstractions that align with the paradigm introduced in Section 1. RLCG defines the task setting, while RACG describes a family of retrieval-augmented methodologies to solve repository-level code generation problems. 

### **2.1 Repository-Level Code Generation (RLCG)** 

Repository-Level Code Generation (RLCG) refers to the generation or modification of code in the context of an entire software repository, rather than isolated functions or files. 

Formally, let a repository be denoted as _R_ = _{f_ 1 _, f_ 2 _, . . . , fn}_ , where each _fi_ represents a file containing code, documentation, or configuration. Given a task specification _q_ (e.g., a bug report, feature request, unfinished code snippet), the objective of RLCG is to produce a modification ∆ _R_ such that: 



satisfies both local correctness (syntactic and semantic validity) and global consistency across the repository. 

Typical applications include 

- _Cross-file Code Completion:_ Predicting or synthesizing missing code segments by leveraging repository-wide context, from single lines to full functions. 

- _Issue or PR Resolution:_ Automatically fixing reported problems by locating relevant files and generating patches consistent with project conventions. 

We discuss a broader range of applications in Section 6.1.

Unlike function-level generation, RLCG requires reasoning over long-range dependencies, cross-file interactions, and system-level constraints. The generation process is inherently state-dependent, as intermediate changes may alter the repository structure and influence subsequent decisions. 

### **2.2 Retrieval-Augmented Code Generation (RACG)** 

Retrieval-Augmented Code Generation enhances LLMs with external software knowledge via retrieval. Unlike pure LLM generation, RACG dynamically retrieves relevant information such as code, documentation, or graphs to construct context-aware prompts. 

In its basic form, RACG (Figure 2) consists of two components: (i) **Retriever** _Mr_ , which selects the relevant context _C ⊆R_ given a query or intermediate state. It typically operates through several structured strategies, including _identifier matching_ based on exact names or signatures, _sparse retrieval_ using lexical or sparse-vector methods such as TF-IDF [Manning et al., 2008] or BM25 [Robertson and Walker, 1994], _dense retrieval_ using neural embeddings such as CodeBERT [Feng et al., 2020] or UniXcoder [Guo et al., 2022] with nearest-neighbor search, _graph-based retrieval_ leveraging structures such as abstract syntax trees and call graphs via traversal or subgraph matching, and _hybrid retrieval_ that integrates lexical, embedding, and structural signals to balance precision and recall. (ii) **Generator** _Mg_ is a language model such as GPT-5.5 [OpenAI, 2025a] or CodeLlama [Rozière et al., 2024] that produces code conditioned on the context retrieved.

## **3 Methodology** 

This section outlines the methodology used to conduct a systematic literature review. We adopt a structured review approach inspired by established guidelines in software engineering literature [He et al., 2025, Jiang et al., 2025a, Petersen et al., 2008]. The methodology encompasses research question formulation, data collection, inclusion and exclusion filtering, quality assessment, snowballing, and topic categorization. 

- ➠ **RQ1: How does RACG evolve from simple retrieval paradigms to complex autonomous architectures?** This question investigates the methodological shift from semantic retrieval to structure-aware graph retrieval. It further explores how training-based optimizations and agentic architectures address complex task resolution. 

- ➠ **RQ2: What are the core configurations, task environments, and evaluation practices for RACG systems?** This question examines the ecosystem and implementation of RACG, covering the impact of diverse data sources and programming language paradigms. It also evaluates how downstream tasks and current benchmark metrics reflect the demands of practical software engineering. 

- ➠ **RQ3: What are the concerns of RACG systems and where is its necessity boundary?** This question analyzes key system-level bottlenecks, including reliability, scalability, and structural complexity. It further examines when retrieval remains necessary versus when long-context modeling is sufficient, and outlines directions for bridging this gap toward real-world deployment.

### **3.1 Data Collection Process** 

To address our research questions and construct a comprehensive corpus on RACG, we adopted a systematic two-stage data collection pipeline, with the primary focus placed on **methodological advances** in retrieval-augmented and repository-level code generation. 

In the first stage, we determined our core search keywords by analyzing accepted papers related to this topic. This initial step allowed us to derive and refine a precise set of search terms strongly associated with RACG. 

In the second stage, we collected all publications from leading artificial intelligence and software engineering venues and journals ( `ICLR` , `NeurIPS` , `ICML` , `IJCAI` , `AAAI` , `JMLR` , `ACL` , `EMNLP` , `ICSE` , `FSE` , `ASE` , `TOSEM` , `TSE` , and `ISSTA` ). We then conducted keyword similarity searches across multiple bibliographic platforms, including `ACM Digital Library` , `IEEE Xplore` , `arXiv` , `OpenReview` , and the `ACL Anthology` . For journals and platforms with anticrawling mechanisms, we supplemented automated retrieval with manual scanning. For preprints on `arXiv` , we implemented a hybrid approach: we first queried the arXiv API using the keywords, and subsequently applied similarity filtering to isolate the most relevant papers. 

The search period spanned from January 1, 2023 to March 31, 2026. This process resulted in 243 candidate papers from the targeted conferences and journals, along with 610 papers from `arXiv` . After consolidating these sources and removing duplicates, the resulting candidate pool was screened according to the criteria detailed in Section 3.2. 

### **3.2 Inclusion and Exclusion Criteria** 

A paper was included if it met all the following: 

- The task involves retrieval-augmented, cross-file, or repository-level settings that enhance code generation. 

- The study proposes a novel RAG-based approach or analyzes the impact of retrieval on generation quality. 

- The full text is accessible and written in English. 

A paper was excluded if it: 

- Focuses solely on standalone code generation or static analysis tools without pretrained Language Models. 

- Uses RAG only as a minor component without methodological contribution. 

- Target tasks such as vulnerability or clone detection, or purely retrieval model training without generation (except for issue localization tasks, which are retained despite being purely retrieval-based due to their high relevance to repository-level settings). 

- Presents only conceptual discussions or ethical commentary without technical contributions. 

### **3.3 Quality Assessment and Final Corpus** 

To ensure the rigor and completeness of our review, each candidate article was evaluated for: (1) relevance to RACG, (2) methodological clarity, and (3) reproducibility. Works that did not meet these criteria were excluded. For preprints sourced from `arXiv` , we additionally required a detailed method section and solid experimental results to compensate for the lack of formal peer review. 

Furthermore, backward snowballing was applied to the reference lists of included papers to identify foundational and related works potentially missed by the initial keyword searches. 

After completing these rigorous screening and quality checks, a final corpus of 152 papers was retained, comprehensively covering the intersections of software engineering, natural language processing, and machine learning.

## **4 Core RACG Strategies** 

To systematically organize the RACG literature, we construct a taxonomy of RAG strategies through an iterative analysis of the selected studies. Specifically, we examine the retrieval substrate, context representation, and retrieval mechanisms adopted by prior work, and group methods according to their dominant retrieval characteristics. As illustrated in Figure 6, Retrieval-Augmented Code Generation methods can be broadly categorized into two major paradigms: **non-graph-based** and **graph-based** . We classify methods by their _primary_ retrieval substrate: a method is considered graph-based if its core retrieval mechanism depends on explicitly constructed graph structures, and non-graph-based otherwise. Methods that inject lightweight structural signals but retrieve over flat text collections remain in the non-graph category. Hybrid approaches are grouped according to their predominant component and noted explicitly. The two paradigms are detailed in turn below. 

### **4.1 Non-Graph-based RACG** 

Non-graph-based RAG methods retrieve code without explicit graph structures, treating repositories as flat text collections and identifying relevant context via similarity matching. Early approaches rely on lexical signals (e.g., BM25 [Robertson and Walker, 1994], Jaccard similarity [Jaccard, 1901]) to match identifiers or keywords, but struggle with deeper semantics. Recent systems shift to semantic retrieval using representation learning. Models such as GraphCodeBERT [Guo et al., 2021] and UniXcoder [Guo et al., 2022] encode code into embeddings, enabling similarity matching that better captures functional and contextual relationships. 

Despite their simplicity, these methods remain widely used due to efficiency and ease of integration. Modern RACG systems extend them along two axes: **retrieval strategies** (how to search) and **retrieval content construction** (what to retrieve and how to organize it). Emerging directions further incorporate **static analysis** for structural signals and **command-driven retrieval** for dynamic, interactive context acquisition. 

### **4.1.1 Retrieval Content Construction** 

This line of work asks **_what to retrieve_** . Rather than modifying retrieval algorithms, it improves performance by reformulating queries, restructuring content, and enriching the knowledge base. 

**Query Reformulation and Multi-Perspective Retrieval.** A key issue is the mismatch between query form and code semantics. To address this, methods enhance query expressiveness in two ways. First, _multi-perspective enrichment_ generates complementary query views. ProCC [Tan et al., 2025] combines lexical, hypothesis, and summary views with bandit selection. RLPG [Shrivastava et al., 2023b] samples candidate contexts and learns selection. ReCo [Li et al., 2024a] rewrites queries and code for consistency. AlignCoder [Jiang et al., 2026] further leverages multiple candidate completions to construct richer queries. Second, _conversion-based retrieval_ bridges modality gaps. SACL [Gupta et al., 2025] augments code with semantic descriptions. Kondo et al. [Kondo et al., 2024] convert code to natural language. Code2JSON [Singhal et al., 2025], Chen et al. [Chen et al., 2024], and CodeBridge [Liang et al., 2025] explore structured or alternative matching. Li et al. [Li et al., 2026b] introduce reasoning-based intent synthesis via docstring-like generation.

### **4.1.2 Retrieval Strategy Optimization** 

Retrieval strategy optimization studies **_what_ to fetch,** **_when_ to fetch it, and** **_how much_ to use** . These choices determine whether retrieved context helps or harms generation. Foundational work, like ReACC [Lu et al., 2022], CEDAR [Nashid et al., 2023], and RAP-Gen [Wang et al., 2023], combine BM25 with dense embeddings, leveraging lexical matching for exact identifiers and dense retrieval for semantic similarity. CODEGENAPI [Zan et al., 2025] extends this to private codebases via API signature retrieval. 

**Adaptive Retrieval and Policy Learning.** Static strategies fail to adapt to query complexity and uncertainty. RepoCoder [Zhang et al., 2023a] iteratively refines queries using intermediate generations, while kNM-LM [Tang et al., 2023] injects retrieval selectively for poorly predicted tokens. Other methods learn adaptive policies. kNNTRANX [Zhang et al., 2023b] applies syntax constraints with adaptive weighting. ProCC [Tan et al., 2025] selects retrievers via LinUCB [Li et al., 2010], and FT2Ra [Guo et al., 2024b] uses ∆logits to trigger retrieval. ARCS [Bhattarai et al., 2025] decomposes queries, while CODEFILTER [Li et al., 2025i] and SWE-Fixer [Xie et al., 2025] refine context usage. CodeRAG [Zhang et al., 2025c] introduces log-probability-guided probing and multi-path retrieval. SRACG [Wang et al., 2026c] adds necessity-aware retrieval, multi-objective selection, and preference consistency filtering. 

**Scalable and Information-Efficient Context Selection.** Large repositories exceed context limits, making selection critical. HCP [Zhang et al., 2025b] prunes context via structural reachability, while RepoMinCoder [Li et al., 2024d] optimizes information retention under length constraints. RepoShapley [Huo et al., 2026] models selection as a cooperative game using Shapley values. Efficiency-oriented methods include FastCoder [Zhao et al., 2025a], which adopts speculative decoding with draft-and-verify stages, and SpecAgent [Ma et al., 2026], which precomputes speculative contexts via future-edit prediction. 

**Retrieval Fidelity and Structural Awareness.** Reducing context size does not ensure correctness. CoRet [Fehr et al., 2025] incorporates call-graph structure, CCCI [Jin and Hamdaqa, 2025] filters inconsistent files, and HyRACC [Li et al., 2025a] adaptively fuses model and datastore outputs. To reduce hallucinations, De-Hallucinator [Eghbali and Pradel, 2024] verifies API usage, while Fedrushkov et al. [Fedrushkov et al., 2025] improve retriever robustness via syntactic hierarchy and contrastive learning. Hydra [Le-Anh et al., 2026] further learns dependency-aware retrieval through pairwise classification. 

**Learning from Feedback and Self-Expression.** Retrieval is often decoupled from generation. RepoGenReflex [Wang et al., 2024] introduces a Reflector that generates feedback to guide subsequent retrieval. SelfRACG [Dong et al., 2025a] enables models to express information needs explicitly before retrieval. 

**Low-Resource Retrieval.** In low-resource settings, weak corpora limit retrieval. RAR [Dutta et al., 2024] combines multiple weak sources (e.g., examples, grammar) via dual retrievers, while PERC [Yoo et al., 2025] converts tasks into pseudocode to enable cross-language retrieval.

### **Emerging Direction: Static Analysis Integration** 

A complementary direction incorporates _static analysis_ to provide explicit structural signals (e.g., types, dependencies, execution constraints), overcoming limitations of similarity-based retrieval. These signals can be integrated throughout the pipeline. Representative systems and their integration strategies are summarized in Table 2. STALL+ [Liu et al., 2024a] applies static analysis in prompting, decoding, and post-processing. MGD [Agrawal et al., 2023] enforces type consistency via decoding-time masking. IDECoder [Li et al., 2024c] leverages IDE-level analysis for precise context retrieval. They also support prompt refinement. CatCoder [Pan et al., 2024] uses type-dependency graphs to constrain prompts, while RRR [Deshpande et al., 2024] iteratively refines context with analysis and execution feedback. Overall, static analysis improves robustness and correctness by adding explicit structural constraints. 

### **Emerging Direction: Command-driven Context Retrieval** 

A recent trend shifts retrieval from one-shot context selection to _agent-driven search_ , where LLMs actively decide what to query, which files or symbols to inspect, and when to stop. ToolTrain [Ma et al., 2025c], RepoNavigator [Zhang et al., 2026b], and CodeScout [Sutawika et al., 2026] train agents to conduct multi-step repository exploration through tool calls or terminal commands. GrepRAG [Wang et al., 2026a] shows that LLM-generated `ripgrep` commands can serve as effective retrieval queries, while SWE-Adept [He and Roy, 2026] uses agent-directed traversal to follow relevant dependency paths. 

Overall, command-driven retrieval makes context acquisition more adaptive, reduces irrelevant context, and turns retrieval into a test-time decision process. 

### **Takeaways** 

The two dimensions correspond to core components of the RACG process. Retrieval strategy optimization controls the retriever _Mr_ and its interaction with state _st_ , enabling dynamic context selection. Retrieval content construction defines _C_ ( _R, st_ ), determining how repository information is formatted into model inputs. Together, they form a unified design space balancing adaptability, informativeness, and correctness.

### **4.2.1 Retrieval Content Construction** 

- **Edge Types** Edges define typed relations between code entities. Each edge can be represented as a tuple ( _vi, vj, r_ ), where _vi, vj ∈ V_ and _r_ denotes the relation type. We consider six common types: ➙ **Contain** : Captures structural inclusion, such as classes containing functions or modules containing classes. It may also represent hierarchical containment across multiple code blocks. 

- ➙ **Import** : Encodes static dependencies introduced by language-level import or include statements across modules or packages. 

- ➙ **Inherit** : Represents inheritance relationships between classes, reflecting object-oriented structure. 

- ➙ **Invoke** : Captures call relations between functions or methods, modeling execution-level dependencies. 

- ➙ **Data Flow (Data F.)** : Tracks how data propagates between variables, parameters, or return values. 

- ➙ **Control Flow (Ctrl F.)** : Represents control dependencies induced by conditionals, loops, and branching constructs. 

**Node Types** Nodes correspond to code entities at different levels of granularity, forming a hierarchical representation of the repository: 

- ➙ **Directory** : Represents the top-level physical organization of a repository. 

- ➙ **Module** : Corresponds to a single source file (e.g., `.py` , `.java` , `.cpp` ). Although often referred to as _File_ in prior work, we use _Module_ to emphasize its role as a logical layer between Directory and Class. 

13 

- ➙ **Class** / **Function** : Core semantic units in most programming languages and common targets for retrieval. 

- ➙ **Line** : The smallest addressable unit in code, enabling fine-grained retrieval and alignment. 

### **4.2.2 Retrieval Strategy Optimization** 

Given a repository graph _G_ = ( _V, E_ ), retrieval can be formulated as selecting a subgraph _G_<sup>_′_</sup> = ( _V_<sup>_′_</sup> _, E_<sup>_′_</sup> ) conditioned on a query _q_ . A common workflow first identifies seed nodes via lexical or semantic matching, then expands them to incorporate structural context. 

Expansion strategies determine how structure is utilized. Local methods such as _k_ -NN or _n_ -hop subgraphs capture nearby dependencies; Breadth-First Search emphasizes immediate neighbors, while Depth-First Search explores deeper paths. Some agent-based systems further define specialized primitives over ASTs (e.g., `search_node` , `traverse_graph` [Chen et al., 2025e]). Pruning is typically applied to control context size. 

**Expansion Strategies and Traversal Algorithms.** Existing methods can be viewed as different instantiations of expansion and traversal strategies, including redesigned relevance scoring and diverse search algorithms. RepoHYPER [Phan et al., 2025] follows a search-expand-refine paradigm based on _k_ -NN with a learned link predictor for re-ranking. RepoScope [Liu et al., 2025c] leverages K-means to predict call chains. LingmaAgent [Ma et al., 2025a] and RANGER [Shah et al., 2025] cast traversal as a search problem using Monte Carlo Tree Search. OrcaLoca [Yu et al., 2025] lets LLM schedule retrieval order via relevance scores. SaraCoder [Chen et al., 2025d] improves retrieval diversity using Decaying Subgraph Edit Distance and Maximal Marginal Relevance. InlineCoder [Hu et al., 2026] retrieves callees after drafting code, while CodeGRAG [Du et al., 2025] and GRACE [Wang et al., 2025c] employ Graph Neural Networks to predict node relevance. 

**Integration of External Signals and Databases.** Some approaches incorporate external signals or structured databases. CocoGen [Bi et al., 2024] refines retrieval using compiler feedback, and AutoCodeRover [Zhang et al., 2024a] combines hierarchical search with fault localization. DSrepair [Ouyang et al., 2025a] models code as RDF triples for SPARQL queries, while Abedu et al. [2024] translate natural language into Cypher queries. 

**Graph-Based Reasoning Capabilities.** Other work enhances reasoning over graphs. SWE-Debate [Li et al., 2025b] uses multi-agent debate over fault propagation paths. Prometheus [Chen et al., 2025f] introduces a working memory to avoid redundant reasoning and traversal, and GraphLocator [Liu et al., 2025a] constructs causal graphs for step-by-step root cause analysis. 

### **4.2.3 Observed Design Patterns** 

**Foundational Graph Structure.** Most methods adopt a three-tier abstraction of `Module` , `Class` , and `Function` , connected by `Contain` edges for hierarchy and `Invoke` edges for call relations. This design preserves structure while remaining tractable for language model reasoning. A few approaches use finer granularity for higher precision: PKG [Saberi and Fard, 2025] employs block- and function-level units with pruning, while GraphCoder [Liu et al., 2024c] builds statement-level graphs with control-flow and data-dependence edges, improving local accuracy at the cost of coverage and overhead. 

**Program Dependence Modeling.** Only a subset of methods explicitly model fine-grained dependencies. DraCo [Cheng et al., 2024] captures variable dependencies via extended dataflow analysis, while CodeGRAG [Du et al., 2025], GraphCoder [Liu et al., 2024c], GRACE [Wang et al., 2025c], and SaraCoder [Chen et al., 2025d] incorporate both control flow and data flow. Adoption remains limited due to reliance on language-specific analysis, cross-function complexity, and high construction cost, although such graphs provide the most precise semantics without execution. 

**Knowledge Graph Augmentation.** Some methods extend graphs with repository metadata and external context. ContextModule [Guan et al., 2024] integrates user behavior and code signals, KGCompass [Yang et al., 2025a] links code with issues and pull requests for multi-hop reasoning, and PKG [Saberi and Fard, 2025] unifies code and text into a programming knowledge graph with multi-granularity retrieval. Abedu [Abedu et al., 2024] supports question answering over repository graphs, while Prometheus [Chen et al., 2025f] augments knowledge graphs with working memory for multi-step reasoning. SemanticForge [Zhang et al., 2025d] further applies knowledge graphs to repository-level code generation with correctness guarantees. 

**Multi-Level Graph Integration.** A clear trend is the integration of multiple structural levels within a single system, where different graph representations are assigned complementary roles for context resolution. CoSIL [Jiang et al., 

14 

2025c] adopts a two-stage retrieval pipeline, first locating relevant files via a coarse module-level call graph and then refining context using a function-level graph. LocAgent [Chen et al., 2025e] organizes repositories into a hierarchical dependency graph exposed as an interactive reasoning tool. Beyond structural hierarchies, several frameworks bridge modalities: GraphCodeAgent [Li et al., 2025d] links requirement-level semantics with code structure, while DraCo [Cheng et al., 2024] and CodeGRAG [Du et al., 2025] combine structural topology with semantic data flow to improve retrieval effectiveness. For autonomous exploration, RepoMaster [Wang et al., 2026b] integrates a Hierarchical Code Tree, Function Call Graph, and Module Dependency Graph. GRACE [Wang et al., 2025c] further advances this direction with a multi-level, multi-semantic graph and hierarchical fusion. Finally, GraphLocator [Liu et al., 2025a] constructs a Causal Issue Graph over a Repository Dependency Fractal Structure Graph to explicitly model symptom-to-root-cause paths. 

**Graph Integration into Language Models.** Several works study how to inject graph information into language models. CoCoMIC [Ding et al., 2024] encodes code entities as tokens via causal attention, CGM [Tao et al., 2025] integrates graph structure into attention with dedicated adapters, and CodeRCSG [Jiang et al., 2024] aligns cross-lingual semantic graphs with model representations. SemanticForge [Zhang et al., 2025d] incorporates graph constraints into beam search with formal verification. 

### **Takeaways** 

Taken together, graph-based RACG can be understood as operating over a structured retrieval space, where graph construction defines the search space, retrieval strategies determine how this space is explored, and integration mechanisms control how structural information influences generation. 

Despite these advances, graph-based methods face a fundamental limitation: their construction pipelines depend on language-specific parsers and static analyzers, which reduces portability across programming languages. 

## **5 System Enhancements & Workflows** 

This section explores the methodologies for optimizing the end-to-end RACG pipeline. While modular RAG can be implemented in a lightweight, zero-shot manner, the inherent complexity often requires a tighter coupling between retrieval signals and the generation process. We categorize works into two primary paradigms: 

First, **Training-Driven Optimizations** (Section 5.1) focus on parameter-level adaptations designed to align the retriever and generator modules. We primarily examine contrastive learning frameworks, architectural fusion techniques, and the emerging trend of using reinforcement learning. 

Second, **Autonomous Agent Architectures** (Section 5.2) shift the paradigm from passive pipelines to dynamic workflows. To analyze these systems, we propose a three-tier classification framework based on autonomy. This allows RACG systems to refine decisions based on execution feedback. 

### **5.1 Training-Driven Optimizations** 

RACG systems can be implemented in a lightweight manner, as work such as DraCo [Cheng et al., 2024] and RepoGraph [Ouyang et al., 2025b] already showed promising results. Some research, however, increasingly treats training as essential for performance. Most approaches are self-supervised or unsupervised, leveraging the inherent structure of code in the absence of labeled data. 

### **5.1.1 Retrieval module training** 

**Contrastive learning and representation alignment.** Most methods train retrievers to align queries and code in a shared space. ReACC [Lu et al., 2022] combines BM25 with a dense retriever and applies contrastive pre-training with code augmentations. InferFix [Jin et al., 2023] aligns buggy code with fixes, while CodeGenAPI [Zan et al., 2025] pairs natural language queries with API documentation. CodeXEmbed [Liu et al., 2025d] unifies multiple tasks in a large-scale contrastive framework. SweRank [Reddy et al., 2025] and SweRank+ [Wang et al., 2025f] optimize retrieval with InfoNCE loss and hard negatives. NEMOTRON-CORTEXA [Sohrabizadeh et al., 2025] generates synthetic query-code pairs, while CONAN-R [Li et al., 2025h] enhances alignment with code–document and another mask entity prediction task. 

15 

**Structure-aware optimization.** Some methods incorporate code structure during training. kNN-TRANX [Zhang et al., 2023b] maps natural language to abstract syntax trees with auxiliary networks for reliability. CodeGRAG [Du et al., 2025] jointly encodes textual and structural views using graph neural networks with structure-preserving learning. 

**Generation-driven and likelihood-based objectives.** Other approaches optimize retrieval based on its impact on generation. CoRet [Fehr et al., 2025] introduces a likelihood-based loss using call graph and file path signals. CodeFilter [Li et al., 2025i] scores retrieved blocks with special tokens. RepoShapley [Huo et al., 2026] models interactions among retrieved contexts via Shapley values. RLPG [Shrivastava et al., 2023b] selects contexts with a trained classifier, while SelfRACG [Dong et al., 2025a] integrates retrieval directly into the model’s hidden states. 

**Multi-stage pipelines and re-ranking.** To balance scale and precision, several methods adopt coarse-to-fine retrieval. SWE-Fixer [Xie et al., 2025] combines BM25 with a fine-tuned LLM model, SweRank [Reddy et al., 2025] adds LLM re-ranking, and CodeRAG [Zhang et al., 2025c] distills re-rankers from stronger models. 

### **5.1.2 Generation module training** 

**Context augmentation and supervised fine-tuning.** The most direct approach concatenates retrieved content with the input prompt. ReACC [Lu et al., 2022] and InferFix [Jin et al., 2023] apply supervised fine-tuning (SFT) on augmented inputs, while R<sup>2</sup> C<sup>2</sup> -Coder [Deng et al., 2024] and RepoFusion [Shrivastava et al., 2023a] extend this idea by incorporating richer structural contexts and task alignment objectives. 

**Architectural fusion and attention mechanisms.** Beyond prompt concatenation, several methods modify architectures for deeper integration. Compression-based approaches such as CoCoMic [Bi et al., 2024], CoRoVA [Cherniuk et al., 2026], and HEF [Sorokin et al., 2026] reduce retrieved content into compact representations for efficient attention. Graph-based methods, including CodeRCSG [Jiang et al., 2024], GRACE [Wang et al., 2025c], and CGM [Tao et al., 2025], jointly model structural relationships via GNNs or subgraph pre-training. Other designs, such as CONAN-G [Li et al., 2025h], leverage dual-view representations and FiD architectures to enhance semantic fusion. 

**Reasoning trajectories and distillation.** To improve performance on complex tasks, some works incorporate reasoning supervision. SWE-Fixer [Xie et al., 2025] uses chain-of-thought (CoT) training for patch generation, while LocAgent [Chen et al., 2025e] distills planning trajectories from larger models into smaller ones. Other approaches explicitly model developer intent by generating intermediate representations (e.g., docstrings) to guide reasoning [Li et al., 2026b]. 

**Advanced training paradigms and domain adaptation.** More advanced strategies refine training objectives and curricula. RepoFormer [Wu et al., 2024] learns when to do retrieval, while CMFT [Sagtani et al., 2025] adopts curriculum learning for robustness. SRI [Zhang et al., 2026a] reframes completion as dynamic editing, and domain-specific tuning is explored in DroidCoder [Yu et al., 2024b] and RTLRepoCoder [Wu et al., 2025]. 

### **Emerging Direction: Reinforcement learning for retrieval and generation alignment.** 

To bridge the gap between retrieval and generation objectives, reinforcement learning (RL) is increasingly adopted. Methods such as RLCoder [Wang et al., 2025e] and AlignCoder [Jiang et al., 2026] optimize retrievers using generator feedback (e.g., perplexity), while SemanticForge [Zhang et al., 2025d] trains query planners with REINFORCE. Two-stage pipelines combine SFT with preference optimization (e.g., PPO in RRG [Gao et al., 2024a], DPO in CoLA [Li et al., 2025e]) to improve alignment and reduce hallucination. RL also powers autonomous code agents such as RepoSearcher [Ma et al., 2025c], RepoNavigator [Zhang et al., 2026b], and CodeScout [Sutawika et al., 2026]. Even outside RAG, works like SoRFT [Ma et al., 2025b] and CoLT [Li et al., 2025f] highlight RL’s broader impact on improving code generation quality. 

16 

### **Takeaways** 

Overall, training is crucial for RACG performance, but must align with task requirements and supervision. Key principles include: 

- **Separate signals for retrieval and generation.** Fine-tuning the generator alone is often insufficient; retrievalspecific or joint objectives are needed when retrieval quality is the bottleneck. 

- **Contrastive learning dominates retrieval training.** It effectively exploits code structure (e.g., transformations, bug–fix pairs) without costly annotation. 

- **Reinforcement learning enables alignment.** It helps models learn when and how to use retrieved context, especially in multi-hop or ambiguous scenarios.

Although recent RACG methods improve retrieval and context construction, many still operate as static, one-shot pipelines that cannot revise decisions based on intermediate outcomes. This limitation is especially evident in repositorylevel tasks (e.g., bug fixing and multi-file editing), which require iterative exploration, error correction, and interaction with external signals. 

Agent-based architectures address this by enabling iterative decision-making, structured planning, and environment interaction, transforming RACG into dynamic, feedback-driven workflows. This allows models to decompose tasks, adapt retrieval and generation, and recover from errors. Despite broad adoption across domains, the definition of an “agent” remains inconsistent. In this work, _we define an agent as a system that perceives its environment, makes decisions via planning or learned policies, and iteratively executes actions to achieve goals without rigid control flow._ 

To analyze agent-based RACG systems, we propose a three-tier taxonomy (Figure 7 and 8) based on autonomy: 

- **Level 0: Non-agent systems** —Static pipelines without iterative feedback, where retrieval and generation are performed in a single pass. 

- **Level 1: Partial agent systems** —Systems with an explicit iterative feedback loop, where intermediate outputs (e.g., generated code, execution signals, or retrieved context) are used to refine subsequent decisions, but without autonomous planning or tool orchestration. 

- **Level 2: Fully autonomous agents** —Systems that perform goal-directed reasoning with autonomous planning, multi-step decision-making, and interaction with external tools or environments. 

### **5.2.1 Level 0: Non-agent Systems** 

Most RACG approaches fall under Level 0, relying on fixed pipelines without dynamic decision-making. While effective for goal-driven tasks, this design lacks adaptivity for complex, multi-step repository problems. Agentless [Xia et al., 2025] exemplifies this paradigm with a three-phase pipeline: hierarchical localization (repository _→_ file _→_ lines), patch generation, and regression-based validation. By avoiding agentic behavior, it achieves strong interpretability and low computational cost, while still reaching competitive performance (e.g., 32% on SWE-bench Lite).

Notably, most training-intensive RACG systems also remain at this level, as retrievers and generators are often optimized independently and cannot adapt during inference, creating a gap between training-time optimization and runtime flexibility. 

### **5.2.2 Level 1: Partial Agent Systems** 

Level 1 systems introduce iterative feedback loops, where intermediate signals (e.g., partial outputs, compiler feedback, or retrieved context) refine subsequent steps. Unlike Level 2, they do not require full planning or autonomous control. Architectural interoperability with agent frameworks, such as RepoGraph [Ouyang et al., 2025b] and RepoLens [Wang et al., 2025f], does not, by itself, constitute agentic behavior; such systems are therefore more appropriately classified as Level 1. 

The other Level 1 systems can be grouped into three patterns. First, **self-guided iteration** , where model outputs guide retrieval, as in RepoCoder [Zhang et al., 2023a], FT2Ra [Guo et al., 2024b], and FastCoder [Zhao et al., 2025a]. DeHallucinator [Eghbali and Pradel, 2024] further filters hallucinated APIs during iteration. Second, **environment-driven feedback** , where external signals guide refinement. CocoGen [Bi et al., 2024] uses compiler feedback, EvoR [Su et al., 2024] incorporates execution and web signals, and other works refine outputs using domain constraints or human feedback [Li et al., 2026b, Tony et al., 2025]. Third, **coarse-to-fine strategies** progressively narrow the search space. CoSIL [Jiang et al., 2025c] moves from file-level to function-level reasoning, while APT [Zhang et al., 2024b] prioritizes simpler dependencies before complex ones. 

A key challenge is stability: iterative loops may introduce error accumulation or semantic drift, requiring better control mechanisms or human-in-the-loop designs [Zhang et al., 2023a]. 

### **5.2.3 Level 2: Fully Autonomous Agent Frameworks** 

A growing number of RACG systems fall under Level 2, featuring fully agentic architectures with autonomous planning, tool usage, and multi-step reasoning. Unlike Level 1 systems that rely on predefined feedback loops, these systems act as goal-directed agents that dynamically explore and operate within repository environments. Existing approaches can be grouped into three main design patterns. 

**Tool-augmented systems.** These systems rely on structured tools to navigate repositories, spanning multiple levels of abstraction. At the command level, RepoNavigator [Zhang et al., 2026b] uses a _jump_ tool for symbol retrieval, while CodeScout [Sutawika et al., 2026] operates purely via Unix terminal commands. At the software engineering level, tools based on Abstract Syntax Trees (ASTs) and the Language Server Protocol (LSP) enable precise static analysis, as seen in RRR [Deshpande et al., 2024], NEMOTRON-CORTEXA [Sohrabizadeh et al., 2025], and AutoCodeRover [Zhang et al., 2024a]. Graph-based systems such as GraphCodeAgent [Li et al., 2025d], LocAgent [Chen et al., 2025e], and RepoMaster [Wang et al., 2026b] introduce traversal tools for repository graphs. Domain-specific frameworks include 

18 

RTLFixer [Tsai et al., 2024] (Verilog compiler) and iSWE [Ganhotra et al., 2026] (CLDK for Java analysis). At the most general level, SWE-agent [Yang et al., 2024] defines an Agent–Computer Interface, while OpenHands [Wang et al., 2025d] provides a unified environment for command execution, browsing, and editing. 

**Multi-agent coordination.** These systems decompose tasks across multiple specialized agents. Role-based designs separate responsibilities, e.g., CodexGraph [Liu et al., 2025b] (natural language vs. Cypher query generation) and SWE-Exp [Chen et al., 2025c] (Instructor vs. Assistant). SpecAgent [Ma et al., 2026] combines Retriever and Forecaster agents. Task-level decomposition is also common, particularly separating localization and editing, as in GraphLocator [Liu et al., 2025a], iSWE [Ganhotra et al., 2026], SWE-Adept [He and Roy, 2026], and SRI [Zhang et al., 2026a]. More complex pipelines include Prometheus [Chen et al., 2025f] (knowledge graph integration) and InfCodeC++ [Dong et al., 2025b] (Reproducer, Patch, Selector agents). Beyond pipelines, SWE-Debate [Li et al., 2025b] introduces structured debate, while HCAG [Wu and Deng, 2026] employs cooperative game-inspired collaboration. 

**Planning and search-based exploration.** These systems explicitly explore large search spaces. Tree-based methods such as RANGER [Shah et al., 2025] and LingmaAgent [Ma et al., 2025a] apply Monte Carlo Tree Search (MCTS). Efficiency-oriented designs include OrcaLoca [Yu et al., 2025] with action scheduling and context pruning and ARCS [Bhattarai et al., 2025] with plan-conditioned retrieval with tiered control. SweRankAgent [Wang et al., 2025f] structures exploration into search, reasoning, reformulation, and aggregation, while ZeroRepo [Luo et al., 2026] applies an explore–exploit strategy over a feature tree for scalable codebase generation. 

A defining feature of Level 2 systems is their ability to enable open-ended exploration and adaptive decision-making. However, this flexibility introduces challenges in efficiency, controllability, and reliability at scale. 

### **Emerging Direction: Agentic Search Instead of Traditional RAG** 

The shift from traditional RAG to Agentic Search reflects a move from passive similarity matching to active exploration. Claude Code [Anthropic, 2025a] exemplifies this paradigm by replacing static embeddings with dynamic tool usage. Instead of querying a fixed index, it leverages terminal utilities such as `grep` , `ls` , and `cat` within a continuous Plan–Act–Observe loop. This grounds reasoning in the live filesystem state, improving precision and enabling real-time dependency tracking. As discussed in Section 4.1.2, this aligns with commanddriven context retrieval, and is increasingly adopted in systems such as CodeScout [Sutawika et al., 2026]. 

### **Takeaways** 

RACG agent architectures span a broad spectrum: Level 0 systems offer simplicity and strong baselines; Level 1 introduces iterative feedback for moderate adaptivity; and Level 2 enables full autonomy through planning, tools, and collaboration. Bridging the gap between Level 0 efficiency and Level 2 capability remains a key research challenge. 

## **6 Downstream Tasks and Benchmarks for RLCG** 

Since RACG is a broad topic, the benchmark landscape is highly fragmented, with many heterogeneous and loosely defined tasks. To ensure clarity and reliability, we focus only on formally defined benchmarks that are directly relevant to RLCG, centering on retrieval-augmented code generation rather than loosely related problems. 

### **6.1 Downstream Tasks** 

Before the emergence of RLCG, code intelligence research had already explored retrieval-centric tasks such as **code search** [Yin et al., 2018], which evaluates a model’s ability to retrieve or synthesize code from natural language queries, as well as **bug or vulnerability detection** [Li et al., 2018], which emphasizes identifying issues using retrieved evidence. With the rise of large language models, RLCG shifts the focus toward stronger _generation_ capabilities, integrating retrieval to support reasoning and synthesis rather than serving as the primary objective. 

RLCG systems have since been applied to several key downstream tasks. The most prominent are **cross-file code completion** and **GitHub issue resolution** , both discussed in Section 2.1. These tasks reflect realistic software engineering scenarios that require reasoning beyond a single file: the former predicts missing code using repository context, while the latter automates bug fixing or feature implementation based on issue descriptions. 

Another important setting is **coding ability evaluation** , represented by benchmarks such as HumanEval [Chen et al., 2021] and MBPP [Austin et al., 2021]. Although less grounded in real-world workflows, these benchmarks provide 

19 

standardized environments to assess whether RLCG improves reasoning and code synthesis under external knowledge augmentation, and enable controlled comparisons with other techniques such as instruction tuning or chain-of-thought prompting. 

Beyond these, RLCG has also been applied to **program repair** [Berabi et al., 2021] and **test generation** [Alshahwan et al., 2024], which focuses on synthesizing unit tests or assertions. Emerging directions further include **theory-to-code translation** [Wu and Deng, 2026] and **repository-level monitoring, editing, and refactoring** [Bairi et al., 2024]. Together, these tasks highlight the versatility of RLCG across multiple dimensions of software engineering. 

### **6.2 Benchmarks** 

We now turn to benchmarks for evaluating RLCG systems. Many works rely on self-constructed benchmarks, as they are easy to build and can highlight specific model strengths. However, this practice hinders fair and consistent comparison across systems. To ensure rigor, we include only benchmarks adopted by multiple works and distinguish two roles: 

- **RLCG-direct benchmarks** : Designed for repository-level or cross-file generation, where retrieval over a codebase is intrinsic. These provide the primary evidence for evaluating RLCG systems. 

- **General-purpose coding benchmarks** : Standalone tasks (e.g., algorithmic problems, docstring-to-code) that do not require repository context. These serve as _auxiliary evidence_ for assessing base LLM capability, but not RLCG effectiveness.

## **7 Configurations for RACG Systems** 

This section summarizes key configurations that shape RACG performance and scope. **Data Sources** (Section 7.1) highlight the shift from repository-local inputs to diverse, task-specific signals. **Programming Language Support** (Section 7.2) reviews the Python-centric landscape and motivates cross-lingual frameworks for real-world use. **Backbone Models** (Section 7.3) discusses model choices for retrieval and generation, along with their trade-offs. 

### **7.1 Data Source** 

In RACG, retrieval typically operates over the target repository, sometimes augmented with API documentation [Cheng et al., 2024, Deng et al., 2025, Gu et al., 2025, Zhang et al., 2023a]. Recent work broadens this scope with task-specific resources, which can be grouped into four categories. 

**General-purpose and web corpora.** Some methods incorporate external programming-related text. PKG [Saberi and Fard, 2025] uses Q&A datasets and tutorials as general knowledge, while EvoR [Su et al., 2024] integrates heterogeneous web content (e.g., blogs, discussions, documentation, and execution feedback) into a unified, evolving knowledge base. 

**Domain knowledge.** Other approaches leverage specialized corpora or constraints. DeepV [Ibnat et al., 2025] reuses VerilogDB [Calzada et al., 2025] for hardware tasks. RTLFixer [Tsai et al., 2024] retrieves expert explanations for syntax errors, while CodeGuarder [Lin et al., 2025] and SecGuide-based methods [Tony et al., 2025] incorporate vulnerability patterns and secure-coding rules. 

**Repository-level structural and relational knowledge.** Several systems exploit relations within or across repositories. A<sup>3</sup> -CodGen [Liao et al., 2024] links local context with global module structures and libraries. Abedu et al. [2024] construct repository knowledge graphs from commits, issues, and files. RepoMaster [Wang et al., 2026b] builds multi-level graphs (e.g., call graphs, dependency graphs) across repositories and retrieves task-relevant components. 

**Experience and behavior traces.** Another line leverages past interaction traces. ContextModule [Guan et al., 2024] mines real editing behavior, SWE-Exp [Chen et al., 2025c] stores repair trajectories, and ReCode [Wang et al., 2025c] collects buggy–fixed pairs. Beyond code, Kranti et al. [2024] use human interaction traces (e.g., collaborative building actions) as retrieval signals.

### **7.2 Programming Language Support** 

We analyze programming language usage in RACG systems based on explicit mentions in prior work, including _cross-lingual transfer_ . As shown in Figure 9, **Python** dominates (111 occurrences), likely due to its prevalence in AI and data science, flexible syntax, and strong ecosystem. **Java** follows (50), reflecting its role in enterprise systems. **C++** and **JavaScript** appear less frequently (8 each), while **TypeScript** and **C#** indicate continued interest in statically typed languages. This distribution shows a strong Python-centric bias in RACG research. Statically typed languages introduce additional challenges in structure, tokenization, and generation fidelity. As a result, bridging the gap between academic settings and heterogeneous industrial repositories remains an open problem, further compounded by benchmark bias (e.g., SWE-bench is Python-only). 

### **Emerging Direction: Universal Language Support** 

Cross-language capability is increasingly important for RACG. `Zhu et al.` [Zhu et al., 2025] show that crosslanguage retrieval can improve multilingual code generation, enhancing robustness and generalization. Many approaches map different languages into unified representations. `Code2JSON` [Singhal et al., 2025] converts code into structured natural language features via zero-shot LLMs. `CodeXEmbed` [Liu et al., 2025d] unifies retrieval tasks across text and code. `CodeRCSG` [Jiang et al., 2024] builds cross-lingual semantic graphs using GNNs, while `Prometheus` [Chen et al., 2025f] constructs unified knowledge graphs across languages. Other works leverage the Language Server Protocol (LSP) for standardized multi-language support. `HCGS` [Sounthiraraj et al., 2025] uses a modified `multilspy` client, and `ChatLSP` [Blinn et al., 2024] provides unified contextual services across languages. 

### **7.3 Backbone Models for Retrieval and Generation** 

We categorize and list the commonly used backbone models in RACG systems. We note that the models included here are representative rather than exhaustive, aiming to cover widely adopted examples across academic literature. 

**Dense Retrieval Models.** Dense retrievers map queries and code into continuous vector spaces using neural encoders. **UniXcoder** [Guo et al., 2022] leverages ASTs and comments with prefix-adapters and contrastive learning for accurate embeddings. **CodeT5** [Wang et al., 2021] incorporates identifier-aware pre-training to better capture semantic signals. **Voyage-Code** [Voyage AI, 2024] improves multilingual retrieval via Matryoshka learning and quantization-aware training. **Stella** [Zhang et al., 2025a] uses multi-stage distillation for strong semantic representations. **GraphCodeBERT** [Guo et al., 2021] models data flow dependencies beyond syntax, while **CodeBERT** [Feng et al., 2020] is effective for NL–PL tasks such as search and documentation. **Ada-Embedding-002** [OpenAI, 2025b] provides general-purpose text–code embeddings with strong retrieval performance.

### **Takeaways** 

Backbone selection in RACG involves key trade-offs: 

- **Retrieval vs. context window:** Dense retrieval scales to large codebases, while long-context models simplify pipelines but incur higher cost and latency. 

- **Sparse vs. dense retrieval:** Sparse methods (BM25) are efficient for keyword matching, whereas dense retrievers better capture semantics at higher cost. 

- **Model size vs. deployment:** Smaller open models are accessible, while proprietary models lead performance; practical use depends on task complexity and system constraints. 

## **8 Discussion and Future Directions** 

This section synthesizes the critical perspectives of RACG. As the field transitions from static augmentation to autonomous engineering, we analyze the critical boundaries of security, the necessity of retrieval in the era of expanding context windows, and the remaining bottlenecks that define future research opportunities. 

### **8.1 Security and Reliability** 

The integration of RAG into repository-level development introduces a unique attack surface spanning both the generation and retrieval modules. On the generation side, LLMs risk inheriting insecure coding patterns from their training data, which often contains vulnerable open-source projects. On the retrieval side, knowledge base poisoning is a major concern. For instance, ImportSnare [Ye et al., 2025] attack demonstrates that crafted malicious documentation can outrank safe resources, leading to the retrieval of harmful contexts [Ye et al., 2025]. DrainCode [Wang et al., 2026e] introduces LLM-Denial-of-Service, where the model is manipulated into generating excessively verbose code to exhaust computational resources. Furthermore, VenomRACG [Li et al., 2025g] demonstrates that a poisoned retriever can be trained to prioritize pre-defined vulnerable code when triggered by specific malicious queries. 

To mitigate these risks, several safety-driven architectures have emerged. CodeGuarder [Lin et al., 2025] proposes that retrievers should also inject security knowledge. Tony et al. [2025] combine security knowledge injection with a self-feedback loop. RESCUE [Shi and Zhang, 2026] introduces a systematic defense through a Hierarchical Security Knowledge Base and Hierarchical Multi-faceted Retrieval. 

24 

### **8.2 The Necessity Boundary: RAG vs. Long-Context LLMs** 

The effectiveness of RAG is context-dependent, and retrieval does not always guarantee better performance. PENG et al. [2025] show that long-context models can match or outperform RAG on small, well-structured repositories, while RAG becomes advantageous as repository size and complexity increase. 

Several studies demonstrate the benefits of retrieval. CodeGen4Libs [Liu et al., 2023] validates the usefulness of retrieval for library-oriented generation through user studies. Chen et al. [2025a] show that RAG improves performance on uncommon APIs and remains robust to mild noise, with BM25 performing strongly. Yang et al. [2025c], Galimzyanov et al. [2025] and Hostnik and Robnik-Šikonja [2025] further report consistent gains from retrieval, especially when combined with effective fusion and selection strategies. 

Other work explores replacing RAG with stronger long-context modeling. SelectSolve [Jiang et al., 2025b] shows that providing the full repository to a long-context model can rival or exceed agent-based systems. Additional approaches use hierarchical summarization, reinforcement learning, or tool-aware training (e.g., SoRFT [Ma et al., 2025b], CoLT [Li et al., 2025f], ToolGen [Wang et al., 2025b]) to improve context utilization without explicit retrieval. 

Industry results also highlight trade-offs. Retrieval improves large-scale systems such as Tencent’s WeChat codebase [Yang et al., 2025d], and combining RAG with fine-tuning yields further gains [Wang et al., 2025a]. However, fine-tuned models can better capture domain-specific conventions (“dialects”) [Finkler et al., 2026], suggesting limits to retrieval alone. 

### **Takeaways** 

RAG is not universally superior. It excels in large or complex repositories, while long-context models can suffice in smaller settings. Effective systems often combine retrieval, model capacity, and fine-tuning, highlighting a key trade-off between context length, retrieval cost, and adaptability. 

### **8.2.1 Limitations of Existing Approaches** 

Despite rapid progress, current RACG systems still face several important limitations in repository-level software engineering. 

**Retrieval and context construction remain difficult.** Non-graph-based approaches often retrieve fragmented repository chunks that fail to preserve long-range semantic dependencies, while graph-based systems introduce substantial overhead in graph construction and traversal [Du et al., 2025, Wang et al., 2025c, Zhang et al., 2025e]. Their effectiveness also heavily depends on language-specific parsers and static analysis quality, limiting portability across repositories and programming languages [Cheng et al., 2024, Liu et al., 2024a]. In addition, retrieval and generation are still frequently optimized separately, creating a disconnect between retrieved context quality and downstream generation utility [Dong et al., 2025a, Fehr et al., 2025]. 

**Agentic RACG systems often trade adaptivity for efficiency.** Recent agent frameworks enable iterative search, planning, and tool usage, but they also introduce substantial context and computation overhead [Sutawika et al., 2026, Yang et al., 2024]. Multi-step workflows may accumulate noisy context or redundant exploration steps as repositories scale [Chen et al., 2025f, Shah et al., 2025]. At the same time, simpler pipelines such as Agentless can achieve competitive performance with significantly lower cost, suggesting that complex agentic workflows are not always necessary [Xia et al., 2025]. 

**Current evaluation settings still lack realism and robustness.** Most benchmarks focus on relatively small repositories, synthetic tasks, or Python-centric ecosystems, while repository evolution, collaborative workflows, and multi-language dependencies are rarely modeled explicitly [Jimenez et al., 2024]. Recent studies further show that static benchmarks may suffer from contamination and benchmark saturation [OpenAI, 2026]. Moreover, most RACG systems are still evaluated in isolated environments rather than integrated software engineering ecosystems such as IDEs, CI/CD pipelines, and collaborative development workflows [Wang et al., 2025d, Yang et al., 2024]. 

### **8.2.2 Future Directions** 

**RACG systems should move beyond text-only repositories toward richer software artifacts.** Future systems can leverage issue discussions, documentation, execution logs, commit histories, and architectural diagrams to improve semantic grounding in underspecified or evolving tasks [Guan et al., 2024, Yang et al., 2025a]. At the same time, multilingual repository support remains increasingly important, as modern software projects often combine multiple programming languages and frameworks within a single codebase [Jiang et al., 2024, Yoo et al., 2025]. 

25 

**Scalable repository-level reasoning and realistic evaluation remain essential research directions.** Recent work increasingly explores hierarchical retrieval, memory compression, and long-context reasoning to support repositoryscale understanding with manageable computational cost [Bogomolov et al., 2024, Huo et al., 2026, Ma et al., 2026]. Meanwhile, future benchmarks should better reflect practical software engineering workflows such as repository evolution, CI/CD integration, package migration, and collaborative development [Li et al., 2026a]. Beyond pass@k or patch correctness, evaluation should also measure factors such as execution efficiency, integration consistency, maintainability, and developer utility [Jimenez et al., 2024]. 

**Agentic software engineering workflows are becoming a central paradigm for RACG.** Recent systems such as SWE-agent, OpenHands, Claude Code, and Codex demonstrate a shift from static retrieval-and-generation pipelines toward interactive software engineering agents capable of repository navigation, iterative refinement, and environment interaction [Wang et al., 2025d, Yang et al., 2024]. Retrieval is increasingly treated as an adaptive test-time process, where agents dynamically decide what files or resources to inspect during problem solving. Future RACG systems may further support repository-wide coordinated editing tasks requiring continuous reasoning over inter-file dependencies and evolving repository states [Bairi et al., 2024, Wang et al., 2026b]. 

**Bridging retrieval, reasoning, and generation remains the core challenge of RACG.** Earlier code intelligence systems primarily focused on retrieval and matching, whereas modern LLM-based systems emphasize generative capability. Future RACG systems will likely move toward tighter integration between retrieval, memory, planning, reasoning, and generation, where retrieved repository artifacts dynamically guide and constrain generation decisions [Chen et al., 2025f, Dong et al., 2025a, Zhang et al., 2025c]. Achieving this integration is essential for building software engineering agents that are both repository-grounded and capable of adaptive, context-aware reasoning. 

## **9 Conclusion** 

As software engineering increasingly shifts from isolated code completion toward repository-scale reasoning and autonomous development workflows, Retrieval-Augmented Code Generation (RACG) has emerged as a critical paradigm for enabling large language models to operate effectively in real-world environments. Unlike traditional code generation settings, repository-level scenarios require models to continuously retrieve, organize, and reason over evolving contextual information distributed across files, dependencies, documentation, and execution feedback. 

In this survey, we presented a comprehensive review of RACG research with a particular focus on Repository-Level Code Generation (RLCG). We argued that RACG should not be viewed as a static “retrieve-then-generate” pipeline, but rather as a coupled and dynamic process involving context construction, retrieval optimization, generation, and environment interaction. To systematically analyze this rapidly evolving landscape, we introduced a unified analytical framework spanning retrieval substrate, control regime, and evaluation setting. Based on this framework, we organized existing methods across non-graph-based and graph-based retrieval paradigms, training-driven optimizations, and autonomous agent architectures, while also reviewing downstream tasks, benchmarks, and practical system configurations. 

Our analysis reveals several emerging trends in the field. First, RACG systems are evolving from similarity-based retrieval toward structure-aware and graph-driven reasoning. Second, retrieval is increasingly becoming an adaptive and agentic process rather than a fixed preprocessing step. Third, autonomous software engineering agents are transforming RACG from passive generation pipelines into interactive systems capable of planning, tool usage, iterative refinement, and environment-aware decision making. At the same time, important challenges remain unresolved, including scalability, retrieval reliability, long-context efficiency, benchmark realism, cross-language portability, and robustness in dynamic repositories. 

Finally, we highlight the growing importance of understanding the necessity boundary between retrieval and longcontext modeling. While long-context LLMs continue to improve rapidly, repository-level software engineering still fundamentally depends on efficient context selection, structured reasoning, and adaptive interaction with external environments. We believe future RACG systems will increasingly integrate retrieval, reasoning, planning, memory, and execution into unified agentic software engineering frameworks. 

We hope this survey provides a structured foundation for future research and helps bridge the gap between academic advances in code generation and practical AI-powered software engineering systems.
