### **Abstract** 

### **Keywords** 

As the Linux kernel evolves, code comments may become outdated, as the functions they reference can be refactored or removed independently without corresponding updates to the comments. Such _stale function references_ can mislead maintainers and thus hinder code comprehension. Prior work on detecting code-comment inconsistency mainly focused on addressing semantic misalignment between Javadoc comments and their directly annotated functions, making them inapplicable to this type of _externally induced_ staleness in the Linux kernel. Therefore, we propose ReCite, a threestage approach to identify and repair such stale references: (1) detecting unresolved _function-form symbols_ —symbols in comments that appear to reference functions but for which no matching function can be found in the current codebase, (2) tracing the evolution history of each unresolved symbol through the Git history, and (3) generating LLM-based repair suggestions grounded in the evolution history and current code context. On Linux kernel v6.18-rc1, ReCite detects 869 stale references with generated repair suggestions. A manual evaluation on 200 sampled repairs shows that 178 (89.0%) provide useful repair guidance, with 85 (42.5%) directly applicable. Of our 75 submitted patches, 50 have been accepted. We also empirically study all unresolved function-form symbols.

### **1 Introduction & Motivation** 

In modern iterative development, code undergoes frequent refactoring as part of routine maintenance [5, 9, 34]. The Linux kernel, which is one of the world’s most actively maintained codebases, typically ships every two to three months with each cycle absorbing about 13,000 changesets [42]. Such changes, however, do not always extend to the comments: existing automated refactoring approaches are primarily proposed for syntactic code elements, instead of unstructured comment texts, making comments easily outdated during code evolution [31]. The lack of update to relevant comments has also been substantiated by a large-scale empirical study [44]. Within these outdated comments, a particularly harmful case is the _stale function reference_ , where the comment of a given function typically mentions another function that has been refactored or removed and thus no longer exists in the current codebase. Such references matter because they capture repository-level knowledge from the original developers that links code entities across the codebase. Once stale, they reduce comment usefulness and increase the maintenance burden as the codebase evolves [8, 36].

These stale references can affect more than comment readability. Figure 2 shows a case where a comment describing a conditional exit refers to hw_perf_group_sched_in(), a function that no longer exists in the current codebase. To repair this unresolved reference, we traced back to commit e7bef6b (January 2010), where the comment was originally written, and found that hw_perf_group_sched_in() was defined at line 992 of the same file. We then tracked the function’s subsequent evolution and found that it was completely removed in commit a13c3af (April 2010). This removal not only rendered the comment stale, but also left the conditional branch “if (!n_ev) return 0;” as unreachable dead code. Such dead code unnecessarily inflates the codebase that maintainers and security auditors must reason about—a well-recognized concern in software debloating and kernel attack-surface reduction [10, 28]. We have submitted a patch that removes both the outdated comment and the dead code. This case illustrates that stale function references are not merely a documentation problem—they can signal latent logical defects that may otherwise go unnoticed. 

Linux kernel developers have also noticed such stale references in practice. For example, commit b7dd80f removed two references to the deleted scan_swap_map_slots() from comments. Nevertheless, such fixes remain isolated and manual, and the kernel still lacks a systematic approach to (i) scan the codebase for stale function references, (ii) trace when and why a reference became _unresolved_ (i.e., no matching function can be found for the symbol in the codebase), and (iii) generate history-grounded repairs at scale. 

To bridge this gap, we propose ReCite, a three-stage approach for automatically identifying and repairing stale function references in Linux kernel comments: (1) Given a kernel snapshot, ReCite first extracts _function-form symbols_ (i.e., symbols written as “foo()” that appear to reference a function or a function-like macro) from all comment blocks. It then checks whether they are resolvable (i.e. the matching function can be found) in the current codebase, using grep combined with Coccinelle [25], a semantic patching framework for C code. (2) For each unresolved symbol, ReCite traces back to the commit where the reference was introduced and identifies the function actually intended by the comment via large language model (LLM)-based entity selection, since static analysis alone cannot disambiguate among same-name candidates. It then tracks the function’s evolution forward—through renames, splits, and removals—to construct an evolution tree. (3) Finally, ReCite prompts an LLM with the evolution tree and relevant context to generate a history-grounded repair suggestion. 

We evaluate ReCite on Linux kernel v6.18-rc1, where it detects 869 stale references and automatically generates corresponding repair suggestions. A manual evaluation on 200 sampled generated repairs shows that 178 (89.0%) provide useful repair guidance, including **85 (42.5%) directly applicable** repairs and 93 (46.5%) partially acceptable ones that need minor manual refinement before direct application. We therefore position ReCite as a decision-support tool that provides helpful repair candidates for maintainers, rather than a fully automatic repair system, at present. We have submitted 75 patches to the Linux kernel; **50 have been accepted** . Specifically, a maintainer who received our patch remarked: “ _We must have missed this comment ... a few years ago._ ” We further did an empirical study on all detected unresolved function-form symbols (5,442 in total) from 8,258 mentions, i.e., occurrences in comments, and established a five-category taxonomy of their underlying causes. 

### **2 Related Work** 

**Code Comment Inconsistency.** Early work relies on rule-based approaches to detect code-comment inconsistency [31, 36–38], while subsequent work shifts towards learning-based methods [17, 29, 46] For example, Panthaplackel et al. [26] use a GNN-based encoder with attention to jointly represent code edits and comments, predicting whether a change invalidates the associated comment at commit time. Other learning-based approaches include CoCC [7], which uses skip-gram embeddings and random-forest classifiers for binary judgments, and CARL-CCI [23], which applies label-aware contrastive learning on structured code diffs. More recently, the task has expanded from detection to automated repair [14, 18, 27], as demonstrated by Rong et al. [32], who fine-tune CodeLLaMA (C4RLLaMA) to both detect and repair inconsistencies. Compared to prior CCI work, we target a long-overlooked problem: a comment may reference a function in a distant file that evolves independently, leaving the comment stale. Existing CCI approaches, developed mostly for Java documentation comments, target local function-summary inconsistencies and thus miss cross-file references (60.5% of our cases; Section 5.2.1). Our C4RLLaMA evaluation further indicates poor transfer to this setting (Section 5.4).

### **3 Proposed Approach** 

Inspired by the manual repair process, we propose ReCite, a threestage approach (Figure 3) for automatically identifying and repairing stale function references in Linux kernel comments. First, we scan the codebase to extract all function-form symbols from comments, and determine which of them are unresolved in the current codebase (Section 3.1). We then trace the evolutionary history of each unresolved symbol to understand why it became invalid (Section 3.2). Finally, we leverage an LLM to generate repair suggestions based on the function’s evolutionary history (Section 3.3). 

### **3.1 Identifying Unresolved Function-Form Symbols** 

We analyzed Linux kernel v6.18-rc1 (HEAD=3a86608). From around 62,000 source files (.c and .h), we extracted 2.27 million code comments, and identified _function-form symbols_ as tokens matching the regular expression “[A-Za-z_][A-Za-z0-9_]*()”. This yields 49,302 

unique symbols across 61,866 comments, totaling 83,241 mentions. Here, a _symbol_ refers to a unique function-form string, while a _mention_ refers to one occurrence of such a symbol in a comment, as one symbol can appear in multiple comments. We then design a two-step validation pipeline to determine whether a given symbol has at least one matching function-level code entity (i.e., can be “ _resolved_ ”) at a specific snapshot. 

**Step 1: Coarse-Grained Search.** For each symbol, we use grep to obtain candidate source files that mention it. We then filter out matches that occur exclusively within comment regions or string literals, ensuring the matched identifier appears in code proper. 

**Step 2: Fine-Grained Static Analysis.** For symbols with candidate files, we further apply static analysis to check whether a matching function definition, declaration, or function-like macro definition exists. We include function declarations as valid evidence of existence, because some functions are implemented in assembly and only declared in C header files. Ignoring declarations would over-approximate the unresolved symbols. We adopt **Coccinelle** [25] for this check. Coccinelle is a code matching and patching engine based on the Semantic Patch Language (SmPL), which was originally developed to support collateral evolution in the Linux kernel. We write an SmPL rule that matches function definitions of the form “name(...){...}”, “type name(...);” and “#define name(...) ...”. 

We denote this two-step pipeline as Resolve( _sym_ , _commit_ ), which returns the set of files that contain the matching function-level code entity for _sym_ in version _commit_ . When restricted to a single file, we write Exists( _sym_ , _file_ , _commit_ ) to denote whether _sym_ can be resolved within a specific file. If no matching entity is found in any candidate file, the symbol is considered unresolved at the queried version. We treat the unresolved symbols in snapshot v6.18-rc1 as the starting point for the subsequent repair pipeline. 

### **3.2 Tracing Function Evolution History** 

To understand why a function-form symbol is unresolvable in the current snapshot, we trace its evolutionary history. We model the historical state of a code entity as a tuple ⟨ _sym, file, commit_ ⟩, where _sym_ is the function-form symbol, _file_ is the source file path, and _commit_ is the Git commit hash. The goal of this stage is to first construct the initial state ⟨ _sym_ 0 _, file_ 0 _, commit_ 0⟩ by locating the code entity that the comment originally referred to (Section 3.2.1), and then trace its evolution forward along the Git history (Section 3.2.2).

_3.2.1 Locating the Referenced Code Entity._ We first return to the commit where the symbol was originally introduced into the comment (i.e., the _symbol-introducing commit_ ), and verify whether it was resolved at that point. For the symbols that are already unresolvable at that time, we manually categorize the underlying reasons in Section 6.1. For the resolvable symbols, we further identify which specific code entity the comment refers to. 

**1) Identify the symbol-introducing commit** : Since files may be renamed over time, we first trace the rename history of the commented file. We then collect commits whose patches involve the referenced symbol under each historical file path. Starting from the earliest such commit, we check whether any comment-region line in the file at that version has a Jaccard similarity ≥ 0 _._ 7 with the symbol-bearing line in the current comment. We use Jaccard similarity rather than exact matching because comments are frequently extended or lightly edited. The 0.7 threshold tolerates minor wording changes while reliably identifying the original introduction. The earliest commit satisfying this criterion is taken as the symbol-introducing commit _commit_ 0. 

**2) Collecting Candidate Code Entities** : We collect all candidate files containing a matching function entity at the symbolintroducing commit by invoking Resolve( _sym_ , _commit_ 0). 

**3) Selecting the Comment-Referenced Code Entity with the LLM** : The static analysis alone cannot determine which candidate code entity the comment actually refers to [22]. The Linux kernel supports multiple architectures, and the same function name may have several architecture-specific implementations simultaneously (e.g., under x86 and ARM). Moreover, some function-form symbols do not refer to any function at all—for instance, “decrypt()” in the comment “ _an optional alternate error code that is acceptable for_ decrypt() _to return_ ” refers generically to a decryption operation rather than a specific implementation. Therefore, we leverage the LLM to identify which candidate the comment refers to. 

We supply the LLM with the target symbol, the comment text at the symbol-introducing commit, the comment-related code context, and the set of candidate entities. The code context is extracted via Tree-sitter [2] from the enclosing or nearest function. Candidates are ordered by path edit distance to the comment’s file. Each candidate is represented by its identifier line together with the three preceding lines, as function signatures may span multiple lines and visibility qualifiers such as “static” may appear on a preceding line. The LLM is instructed to return any one of: 

- the file containing the comment-referenced code entity, 

- NO_MATCHED_DEFINITION if no suitable candidate is found, 

- NOT_A_FUNCTION if the symbol does not refer to a function. 

For functions whose implementations fall outside our *.c/*.h scope (e.g., assembly implementations), the LLM is instructed to select the declaration file closest in path to the comment’s file. To guard against hallucination, we verify whether the returned file path appears in the original candidate list. If not, we retry up to two times, each time providing the LLM with its previous erroneous output as feedback, as prior work [16] has shown that LLM performance improves in early feedback rounds and quickly stabilizes thereafter. If the response remains invalid after all retries, the case is marked as “ _Tracing Inconclusive_ ” and excluded from further tracing. The complete prompt is available in our replication package.

### **3.3 Generating Repair Suggestions with LLM** 

To repair stale references in comments, we generate suggestions based on the evolution history of the referenced code entities. Each stale reference is treated individually. The prompt is organized into four input sections followed by a chain-of-thought analysis request. (The full prompt details are included in our release package.) 

The structured input consists of: **1) Target Comment Context** , which includes the current comment, its file location, the specific stale reference, and the surrounding code context in the current version, i.e., the environment into which the repaired comment needs to fit; **2) Origin Context** , which includes the description of 

the symbol-introducing commit, together with the comment’s code context and the original function’s source at that time, allowing the LLM to contrast the original and current versions and judge whether the comment’s intent still holds; **3) Evolutionary History** , which includes the full evolution tree of the referenced function (in a format similar to Figure 4), followed by detailed change logs, including each function-removing commit’s title and message and a pruned diff restricted to the disappeared entity or its successors; **4) Evolution Outcomes** , where we present the current code of surviving successors in the evolution tree, so the LLM can assess whether they are suitable replacements for the stale reference. 

We then instruct the LLM to reason as follows before answering: **1) Evolution Analysis** : trace the evolution path of the missing function—whether it was simply renamed, had its logic split, or was entirely removed—and identify which surviving function, if any, carries the semantic equivalent of the original reference. **2) Comment Context & Semantic Analysis** : examine the current code context surrounding the comment and assess whether the comment’s original intent remains valid given the code changes. **3) Repair Strategy** : propose a concrete fix by updating the function name, rephrasing the comment when needed, or entirely removing it if it has become obsolete, ensuring the repaired comment fits the current code context. 

Finally, the LLM produces the repaired comment based on the above analysis. For example, for the comment “ _See the link below and_ **_ieee80211_start_scan()_** _for more._ ”, ReCite recommends replacing the stale reference with its core-logic successor ___ieee80211_start _scan_ (Figure 4). This repair has been accepted into the Linux kernel. 

### **4 Experimental Setup** 

We evaluated ReCite on Linux kernel v6.18-rc1 for automatically identifying and repairing stale function references in kernel comments. From this snapshot, we extracted 49,302 unique functionform symbols across 61,866 comments, totaling 83,241 mentions. Using grep with Coccinelle, ReCite flags 8,258 function-form mentions (5,442 unique symbols across 7,111 comments) as unresolved in the current snapshot. Among them, we found 7,177/8,258 (86.9%) mentions were already unresolvable when the symbol was first introduced into the comment; we provide a manual categorization of their underlying reasons in Section 6.1 (only 17.3% of these are genuinely missing functions). For the remaining 1,081/8,258 (13.1%) resolvable mentions, for which at least one same-name candidate can serve as a traceable starting point, ReCite proceeds to construct the evolution history: it first locates a valid referenced code entity for 999 of them (the other 82 lack a valid entity), then successfully traces and repairs 869 of these (the remaining 130 end in _Tracing Inconclusive_ ). **These 869 cases therefore constitute ReCite’s positive predictions for repair-worthy stale function references.** Our manual analysis shows that the majority of these 130 cases are upstream Coccinelle false positives that in fact need no repair (see Section 5.2); accordingly, ReCite does not treat them as repair-worthy stale references and does not present repair suggestions to the user. ### **4.1 RQ1: Detection of Unresolved Symbols** 

As described in Section 3.1, ReCite uses a two-step process to determine whether a symbol is resolved at a given version: a coarsegrained search with grep followed by fine-grained static analysis with Coccinelle. To evaluate the accuracy of this pipeline, we replaced Coccinelle with three other widely used static analysis tools: **Tree-sitter** [2] (a concrete syntax tree parser), **Universal Ctags** [43] (a syntax-based symbol indexer), and **GNU Global** [35] (a project-wide cross-reference tool). Each was configured to check whether a matching function definition, declaration, or functionlike macro definition exists. We also evaluated using grep alone without any fine-grained analysis. We denote the five resulting configurations as Resolve-Coccinelle (grep + Coccinelle, our default), Resolve-TreeSitter (grep + Tree-sitter), Resolve-Ctags (grep + Universal Ctags), Resolve-GNUGlobal (grep + GNU Global), and Resolve-OnlyGrep (grep only, without any fine-grained static analysis). We ran all five configurations on the 49,302 unique functionform symbols extracted from HEAD. 

Among the 49,302 symbols, 3,796 received conflicting resolution results across the five configurations. To establish ground truth, we randomly sampled 200 of these disagreement cases for manual annotation, forming the **Symbol Resolution 200** dataset. Two annotators—both senior undergraduate students majoring in software engineering—independently labeled each symbol as _resolved_ or _unresolved_ at HEAD, by inspecting the source code at the target commit. They first annotated a pilot batch of 20 symbols to calibrate their criteria, achieving a Cohen’s _𝜅_ of 0.89. After resolving disagreements through discussion with the first author, the remaining symbols were split evenly between the two annotators. In the final ground truth, 110 symbols were labeled as _resolved_ and 90 as _unresolved_ . We evaluated all five Resolve variants on this dataset and report precision ( _𝑃_ ), recall ( _𝑅_ ), F1-score ( _𝐹_ 1), and accuracy ( _𝐴𝑐𝑐_ ). 

### **4.2 RQ2: Accuracy of Evolution Tracing** 

For the 1,081 mentions resolvable at their symbol-introducing commit, ReCite constructs the evolution history for repair. We evaluate this stage through two sub-tasks: (1) _comment-reference entity selection_ —whether ReCite correctly identifies the referenced code entity; and (2) _refactoring analysis_ —whether ReCite correctly determines how the entity was changed at function-removing commits. 

**Comment-Reference Entity Selection.** We randomly sampled 200 cases from the 1,081 resolvable mentions to form the **Entity Selection 200** dataset. Two annotators independently labeled each case, determining: (a) whether the symbol refers to a concrete function entity, and if so, (b) which file contains the referenced entity at _commit_ 0. The annotator selected one of: a file path (the entity is found), NOT_A_FUNCTION (the symbol does not refer to a function), or NO_MATCHED_DEFINITION (no suitable candidate is found). The annotators first labeled a pilot batch of 20 cases. At the binary level (entity exists vs. not), they achieved a Cohen’s _𝜅_ of 0.62 (substantial agreement). Among the 16 cases where both identified a valid entity, they agreed on the exact file path in all cases (100%). After resolving disagreements through discussion with the first author, the remaining cases were split evenly between the two annotators. In the final ground truth, 173 symbols were labeled as having a valid code entity, while 27 were not (14 NO_MATCHED_DEFINITION, 13 NOT_A_FUNCTION). 

We also evaluated ReCite on two levels. First, we assessed _entity detection_ : whether ReCite correctly determines that a symbol has a valid code entity. We mapped the output to a binary label: _𝑦_ =1 if ReCite returns a file path; _𝑦_ =0 if it returns NOT_A_FUNCTION or NO_MATCHED_DEFINITION. We then report _𝑃_ , _𝑅_ , and _𝐹_ 1. Second, we assessed _entity localization_ : among the cases where both ReCite and the ground truth agree that a valid entity exists ( _𝑦_ =1), we computed the accuracy of the returned file path, i.e., the proportion of cases where ReCite’s file path matches the annotator’s file path. 

**Refactoring Analysis.** Applying entity selection to 1,081 resolvable mentions, ReCite located a valid referenced code entity for 999 of them. To evaluate how accurately ReCite traces their evolution, we use RefDiff [33], a static-analysis-based refactoring detection tool, as a baseline. Using ReCite, we successfully constructed evolution trees for 869 of 999 candidate mentions, containing a total of 916 unique function-removing commits. The remaining 130 cases ended in _Tracing Inconclusive_ , analyzed in Section 5.2. Using RefDiff, we constructed evolution trees for 903 cases, containing 837 function-removing commits. The two approaches shared 785 removing commits where they analyzed the same code entity ⟨ _sym, file_ ⟩ at the same commit, of which 282 yielded different results. 

We randomly sampled 200 cases from these divergent cases to form the **Refactoring Analysis 200** dataset. For each case—a code entity ⟨ _sym, file_ ⟩ at a specific function-removing commit—the annotator determined whether the entity was _removed_ (deleted without a successor) or _refactored_ . ### **6 Discussion** 

### **6.1 Categorization of Unresolvable Mentions** 

For the 7,177 (86.9%) mentions that were already unresolvable when the symbol was first written into the comment, we conducted a manual categorization to understand their underlying reasons. The first author first performed open coding on 30 randomly sampled cases, establishing the five categories listed below. We then sampled an additional 400 cases to form the **Exist Reason 400** dataset. Three other annotators (also undergraduate students majoring in software engineering) began with a 20-case pilot, achieving a Fleiss’ _𝜅_ of 0.72. After resolving disagreements with the first author, they completed the remaining 380 annotations. All 400 annotated cases fell within the five categories, with no additional category emerging. 

- (1) **Non-kernel Entity** (43/400, 10.8%): the symbol refers to an entity not defined in the kernel source, such as a compiler builtin, a C library function, or a function from an external project. For example, the comment _“CONFIG_UBSAN_TRAP inserts a UD2 when it sees_ **___builtin_unreachable()_** _”_ refers to a GCC compiler built-in, not a kernel function. 

- (2) **Kernel Concept, Not a Function** (153/400, 38.3%): the symbol refers to a kernel entity but does not refer to a function. For example, in comments, “ _invalid_vma()_ ” may denote a functionpointer field rather than a standalone function, and “ _kexec()_ ” can be used as a verb meaning _“perform a kexec operation”_ . 

- (3) **Abbreviation/Wildcard** (113/400, 28.3%): the symbol refers to one or more real kernel functions, but the comment uses an abbreviation or suffix pattern that does not exactly match any function name. For example, the comment _“completion is now handled in the_ **_regular_isr()_** _”_ refers to the function wmt_mci_regular_isr() in the same file, but resolving the abbreviated name _regular_isr_ alone yields no match. 

- (4) **True Missing Function** (69/400, 17.3%): the symbol refers to a specific kernel function that genuinely does not exist at the queried version. We further sub-categorize these cases: 

   - (a) **Typo** (33/69): the symbol is a misspelling of an existing function, e.g., “ _cmpxcgh()_ ” for the actual function cmpxchg(). (b) **Already Obsolete at Introduction** (32/68): the referenced function had already been removed or renamed before the comment was written. For example, the function plug_ctx_cmp() was refactored into plug_rq_cmp() in 2018, but a comment created in 2021 still referenced the obsolete name—likely due to copy-paste from an earlier source. 

   - (c) **Explicitly Declared Absence** (4/69): the comment itself makes clear that the referenced function does not exist, e.g., in a TODO note. 

- (5) **Tool False Positive** (22/400, 5.5%): the function exists at the queried version but was missed by our tool. 

### **6.2 Challenges and Insights** 

As discussed above, both identifying and repairing stale function references are considerably more complex than initially anticipated. We summarize the key challenges and insights below. 

**Challenges in identification.** The difficulty of identifying repair-worthy stale references stems from two sources: the diversity of natural language in comments, and the complexity of the code itself. **On the language side** , developers frequently use functionform symbols to refer to entities that are not kernel-managed functions—compiler built-ins, C library routines (Cat. 1), struct fields, or verbs (Cat. 2). These do not require function-level repair. Beyond non-targets, natural language may also complicate what a symbol actually refers to. Developers may use abbreviations or wildcard-style names (Cat. 3), which turn a one-to-one symbolto-entity mapping into a one-to-many relationship. And the abbreviation could also become stale. For instance, pci_dma_sync() is a shorthand for a family of PCI DMA synchronization functions (e.g. pci_dma_sync_{single_for_cpu, sg_for_device}(), etc.), all of which were removed in commit 7968778 and replaced by the unified dma_sync_* API. Moreover, typos and omitted parentheses (e.g., writing foo instead of foo()) could further increase ambiguity and cause references to escape our extraction. **On the code side** , even when a matching function definition exists, the specific reference may still be stale. For instance, if a comment in an ARM source file mentions platform_cpu_die() but the only matching definition is found under a different architecture (i.e., arch/blackfin/), the reference is still outdated since it clearly does not intend to point there. Such cases (NO_MATCHED_DEFINITION in our entity selection) are effectively a form of Already Obsolete at Introduction, requiring architecture-aware reasoning to disambiguate. Given these complexities, we do not claim to have mapped all stale function references in the Linux kernel. Our approach— anchoring on “symbol()”-form tokens—provides a practical starting point, and we focus repair efforts on the subset where a source entity can be located at the symbol-introducing commit. 

**Challenges in repair.** Tracing a stale reference back to its source entity is a prerequisite for history-grounded repair, yet this cannot always be achieved. The Linux kernel has been under development since 1991, but it only adopted Git in 2005, leaving pre-Git history difficult to access [19]. Moreover, comment authors do not always reference valid entities at the time of writing (e.g., through copy-paste from older code). Combined with non-kernel and non-function references (Cat. 1–3), 7,177 of 8,258 mentions (86.9%) are already unresolvable at introduction. In this work, we focus on the 1,081 resolvable mentions, where a source entity can be located—this also naturally filters out non-kernel entities and other noise, letting us concentrate on cases with clear repair value. Even for these traceable cases, repairing a stale reference is far from simple name substitution. A function’s removal or refactoring often reflects deeper changes in code logic. For example, in the comment _“It must be done after_ xfrm6_policy_check() _, because_ **__decode_session6()_** _uses_ IP6CB() _”_ , _decode_session6() was first renamed to decode_session6() and later refactored to no longer use IP6CB() (commit 7a02070). As a result, the ordering constraint itself no longer holds, and the entire sentence—not just the function name—should be removed. We submitted this repair as a kernel patch, but the maintainer’s response went even further, questioning whether the removal of this constraint makes the repeated fill_cb/restore_cb call pattern it necessitated redundant as well. This suggests that stale comments can signal deeper code-level technical debt. Such cases call for repair strategies that go beyond

### **7 Threats to Validity** 

**Internal validity.** Our Resolve-Coccinelle pipeline operates on unexpanded source text, so it cannot recognize function definitions generated through C preprocessor macros. Coccinelle can resolve this by performing full preprocessing with the kernel build configuration, but this drastically increases analysis time and limits results to the single hardware architecture selected in the config file. Operating on unexpanded source text allows our pipeline to find definitions for all architectures. This trade-off favors precision over recall ( _𝑃_ =96 _._ 7%): Resolve-Coccinelle may over-report unresolved symbols, but rarely misses a genuinely resolved one. For our task, this is the safer direction—over-reported cases are easily filtered during evolution tracing, whereas a missed stale reference would silently forgo repair. Another threat is that we track the function changes commit-by-commit, so a refactoring spread across commits (e.g., delete then re-add) may be misclassified as _Removed_ . To assess this, we sampled 50 cases flagged as _removed_ and compared each deleted body against later-added functions, treating ≥ 50% identifiertoken overlap (Jaccard ≥ 0.5) as a possible multi-step refactoring; none was detected. Further threats stem from our hyperparameters and choice of LLM. For identifying the symbol-introducing commit, we use Jaccard ≥ 0 _._ 7 to match the symbol-bearing comment; rerunning this step at 0.6 and 0.8 changed only 0.86% / 0.85% of commits, suggesting low sensitivity to this threshold. For the LLM, we use DeepSeek-V3.2 as a cost-effective choice with temperature 0 for output stability, following prior SE studies [3, 24]. A stronger model shows better performance, e.g. on the RQ2 Entity Selection 200 dataset, Claude Opus 4.7 [1] improves entity-detection _𝐹_ 1 from 0.964 to 0.975 and file-path match accuracy from 98.3% to 99.4%. This suggests that our results are not tied to the strongest available model and may improve with stronger LLMs. Our prompts use only structured inputs (no Linux-specific few-shot examples), though their effectiveness on other projects requires further evaluation. 

**External validity.** We evaluate ReCite solely on the Linux kernel. Given its scale and complexity, we expect the approach to generalize to other C projects with a Git history. While ReCite’s core idea of static-analysis-assisted LLM reasoning is language-agnostic, its effectiveness on other languages remains to be validated. 

**Construct validity.** All our annotated datasets meet or exceed the minimum sample size for a 95% confidence level with a ±10% margin of error. Two of them— **Symbol Resolution 200** and **Refactoring Analysis 200** —are sampled from cases where tools disagree, which may introduce sampling bias. To verify that tool performance generalizes, we additionally sampled 100 agreement cases for each dataset. On Symbol Resolution, all five Resolve variants achieve 100% accuracy. On Refactoring Analysis, ReCite achieves _𝐹_ 1=0 _._ 891 on binary classification and _𝐹_ 1=1 _._ 00 on successor identification. The lower binary _𝐹_ 1 compared to the disagreement set (0.974) is attributable to 9 borderline cases where the function was deleted but its functionality was merged by another one, leading both tools to label them as _removed_ while annotators favor _refactored_ . The perfect successor identification ( _𝐹_ 1=1 _._ 00) further demonstrates that 

ReCite reliably traces function evolution on both agreement and disagreement cases. Similarly, given the rarity of stale references, RQ4 uses balanced rather than purely random sampling, which may limit our view of their true prevalence across all 83,241 mentions. Nevertheless, on the annotated sample, ReCite achieves high precision with only two false negatives. Additionally, to ensure annotation reliability of our ground truth, all datasets follow a pilot-then-split protocol, and the inter-annotator agreement across pilot batches reaches at least substantial agreement (minimum _𝜅_ = 0.62). Finally, Section 6.1 shows that an unresolved symbol (i.e., one without a matching function) is not necessarily a stale reference requiring repair. And we focus on staleness in the narrow sense of function references, specifically cases where the referenced function has disappeared through code evolution. Cases involving other code entities (e.g. variables), or semantic drift while the referenced function will be our future work. Lastly, given the 42.5% Acceptable rate in RQ3, we position ReCite as a decision-support tool rather than a fully automatic repair system, at present. 

### **8 Conclusion and Future Work** 

We presented ReCite, a three-stage approach for automatically identifying and repairing stale function references in Linux kernel comments. On kernel v6.18-rc1, ReCite extracted 83,241 functionform mentions and detected 869 stale references with generated repair suggestions. A manual evaluation on 200 sampled repairs shows that 85 (42.5%) generated suggestions are directly applicable. To date, 50 of 75 our submitted patches have been accepted. 

In future work, we plan to broaden coverage by handling abbreviations, wildcard-style references, and omitted parentheses. We also aim to explore agent-based approaches that can reason about deeper semantic changes, and to investigate the generalizability of our approach to other large, long-lived C codebases.
