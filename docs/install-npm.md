# npm bootstrap (MBR-906)

`@orthic/membrane` is a thin loader. It maps `process.platform` + `process.arch` to a per-platform native package, validates artifact bytes against `metadata.sha256`, validates signed metadata bound to that digest, then exposes native `dispatch`.

The package contains no Node server core. Unsupported tuples, missing metadata, digest mismatch, invalid signature metadata, failed injected signature verification, or native packages without `dispatch` fail closed before dispatch. `npm/index.mjs` mappings are fixture/template names only; no package is published by this source change.

Consumers provide artifact bytes, release metadata, a loader, and (when cryptographic verification is available) `verifySignature({ artifact, digest, signature })`. Registry publication, native artifact production, signing-key trust, and install acceptance remain release gates.

## Per-platform packages (`npm/platforms/**`)

`npm/index.mjs`'s `PLATFORM_PACKAGES` registry names six `@orthic/membrane-<os>-<arch>` packages, one per npm `os`/`cpu` pair Membrane's release pipeline can eventually target: `darwin-arm64`, `darwin-x64`, `linux-arm64`, `linux-x64`, `win32-arm64`, `win32-x64`. Each has a real, minimal `package.json` scaffold under `npm/platforms/<key>/` declaring `os`/`cpu` so npm's own optionalDependency resolution installs only the one matching the current host — the same mechanism esbuild/swc/napi-rs packages use. `npm/package.json` lists all six as `optionalDependencies`. None of the six carry a `main`, `files`, or bundled binary today: no native artifact has been built or signed by this task (or any task in this lane), so there is nothing real to embed. Embedding a fake one would violate the hard rule that this task resolves and fetches, it does not ship binaries.

`linux-arm64` and `linux-x64` are permanent, declared placeholders: `release/contracts/platforms.v1.json` (MBR-903) defines no Linux release target at all, so no RightKit build will ever populate them through this pipeline. `darwin-x64` and `windows-arm64` are real pipeline targets marked `not-buildable`/conformance-only in `scripts/release/pipeline/platform-targets.mjs` today — real gaps in `apps/membrane-hub`'s packaging config, not this task's to close.

## Resolving MBR-903's pipeline output (`scripts/release/npm/resolve-platform-artifacts.mjs`)

This repo-side (never published) module is the layer this task adds to answer "which npm platform packages does MBR-903's pipeline say are real right now?" It reads MBR-903's immutable `evidence/releases/<releaseId>/release-generation.json` (written by `scripts/release/pipeline/multi-platform-release.mjs --write`, imported here read-only, never re-implemented) and maps each npm platform key to the pipeline target enum that file actually uses (`NPM_PLATFORM_TO_PIPELINE_TARGET`). For a target MBR-903 marked `"verified"`, it returns the exact recorded `{ name, sha256 }`; for anything else — no release-generation recorded yet, `"pending"`, `"not-buildable"`, or no pipeline target at all — it throws a named, message-carrying error (`ArtifactNotVerifiedError` / `NoPipelineTargetError`) instead of fabricating a value. `resolveAllNpmPlatformArtifacts` runs all six and never throws itself, returning an `{ ok, ... }` record per key so every platform's real state is visible in one pass.

Run against this actual checkout today, every npm platform key resolves to a declared gap: only macOS builds are sealed under `.right-release/sealed/` and no `evidence/releases/**/release-generation.json` has been written for any of them (`scripts/release/npm/resolve-platform-artifacts.test.mjs`'s "today's real Membrane checkout ... nothing is invented" test asserts this directly against the live repo root).

## Verified install (`npm/bin/membrane.mjs`)

`npx @orthic/membrane install` is the bootstrapper's one CLI entry point. It calls `selectPlatform` to find the optionalDependency package name npm already selected for this host, dynamically imports it, requires it to export `{ artifact, metadata, dispatch }`, then runs the exact same `bootstrap()` digest+signature verification `npm/index.mjs` already implements before ever calling `dispatch`. Every failure mode is a distinct, named error: unsupported host (`UnsupportedPlatformError`), platform package not installed or missing its verified export (`PlatformPackageMissingError`), digest/signature mismatch (`ArtifactVerificationError`), or no signing trust root configured (`SigningTrustNotConfiguredError` — this package ships no public key, so the default `verifySignature` fails closed rather than fabricating trust; signing-key distribution is MBR-901/MBR-902/MBR-911's release-gate territory, outside this task).

`tests/npm/install-cli.test.mjs` proves the full acceptance path deterministically, without any network or registry access: a correctly signed, matching-digest fixture verifies and dispatches; a digest mismatch and a failed signature both reject with `ArtifactVerificationError` before `dispatch` is ever called; a missing platform package, an export missing `artifact`/`metadata`, and the unconfigured-trust default all fail closed with their own named error.
