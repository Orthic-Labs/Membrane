# Membrane — Portfolio Boundaries and Product Positioning

**Sources of truth for this document:**

- `docs/product.md` — generated product overview (regenerated by `tools/productization/generate-product-truth.mjs`)
- `docs/architecture.md` — generated component / interface inventory (same generator)
- `docs/protocol.md` — generated MCP tool surface contract
- `docs/membrane/capability-matrix.v1.json` — vendored host capability matrix
- `mcp/server.mjs` — live MCP tool inventory
- `engine/Cargo.toml` / `engine/crates/*` — Crypt engine source of truth

This document is hand-written. It is **not** regenerated, and the book-gate
`check-docs.mjs` check does not act on it. It is the single place that defines
**which owner layer owns which kind of feature**, so that two layers never
both claim authority over the same request.

## 1. Product positioning

Membrane is a typed, local, receipt-bearing context layer that sits between an
agent and its sources. It is **not** a model, a router, an agent runtime, or a
shared service. It is positioned as:

- **A context layer**, not a control plane. Membrane returns the smallest
  useful set of current code, rules, decisions, and memory for each task, plus
  a receipt that names what entered context, what did not, and why.
- **A local product**, not a hosted service. All data stays repository-confined
  and loopback-bound. There is no Membrane cloud, no shared index, and no
  cross-repository sync path.
- **A typed contract**, not a heuristic. The MCP tool surface, the `ScopeGrant`
  / candidate / packet / receipt envelopes, and the host capability matrix are
  each their own schema. Membrane fails closed on schema mismatch instead of
  guessing.
- **An honest mirror**, not a marketing surface. Capability levels (L0–L5) are
  derived from `capability-matrix.v1.json`; a host that honestly hits L1 is
  rendered as L1. There is no "fully enforced everywhere" claim.

What Membrane is **not**:

- It is not a substitute for the underlying host's hook or tool system. Hosts
  remain the source of truth for what they can enforce.
- It is not a workspace-coupled memory store. Membrane rejects workspace
  inheritance at the boundary (host that inherits workspace memory is
  classified separately and not promoted to L4+).
- It is not a release pipeline, CI configuration, or hosted runner. This
  repository forbids CI workflows (see `MEMBRANE-NO-CI-WORKSPACE-CONSTRAINT.md`).
- It is not a publisher. The MCP server, the federation gateway, and the
  Crypt engine are local-only; no task adds push, publish, or remote-sync
  verbs.

## 2. Owner-layer taxonomy

Every feature request — meaning every change, issue, or scope-grant candidate
that touches the Membrane surface — must be assigned to **exactly one** of the
following owner layers. Two layers never both claim authority over the same
request. If a request appears to span two layers, the rule is: split it, do not
duplicate it.

| Layer | Symbol | Source of truth | Authoritative for |
|---|---|---|---|
| **Product surface** | `PRODUCT` | `docs/product.md` | What the user sees, names, count claims, and narrative positioning |
| **Protocol surface** | `PROTOCOL` | `docs/protocol.md`, `mcp/server.mjs` | MCP tool names, tool input/output schemas, behavioral contract bounds |
| **Adapter surface** | `ADAPTER` | `docs/membrane/capability-matrix.v1.json` | Per-host honest capability levels, host-specific injection / receipt / gate hooks |
| **Federation gateway** | `FEDERATION` | `mcp/server.mjs` (loopback `/federate`) | Cross-provider routing, concurrency / cancellation / deadline policy, provider fan-out |
| **Crypt engine** | `ENGINE` | `engine/crates/*` | Durable memory, retrieval, telemetry records, on-disk schema, embedding model selection |
| **Generation / docs truth** | `GENERATION` | `tools/productization/*` | Regeneration of generated docs, product-truth gate, README link inventory |
| **Workspace rules** | `RULES` | `AGENTS.md`, `CLAUDE.md`, `docs/agent-rules.md` | Workspace-level conduct, mandatory systems, locked invariants |

The `RULES` layer is reserved for the conduct / invariant surface and is never
the owner of a product feature. It is listed for completeness so reviewers
know that a feature request phrased as "we should be more honest" is a
*content* claim that must still be routed to `PRODUCT` or `PROTOCOL` or
`ADAPTER` based on what it actually changes.

## 3. Boundary rule

**Every feature request must be assigned to exactly one owner layer, and that
layer must be the legitimate source of truth for the change.**

The rule is enforced by the matrix in section 4. The matrix maps each
recognized kind of feature request to the single layer that owns it. If a
request does not fit any row, it is an undefined-shape request and must be
split or escalated before implementation. The matrix is the **assignment
contract**; it is the only source of authority on who owns a request.

The rule is intentionally not phrased as "the most relevant layer." Two
layers always look relevant when a feature touches their boundary. The point
of the rule is that only one layer's source of truth is allowed to change.

### 3.1 Prohibited duplicates

The following would be a violation of the boundary rule and must be rejected
during review:

- A change to `mcp/server.mjs` that also rewrites the tool count claim in
  `README.md` by hand. The tool count in user-facing prose is owned by
  `PRODUCT`, but the count itself is generated by `GENERATION` from the live
  `mcp/server.mjs`. The hand-rewrite is the duplicate, not the ownership.
- A change to `capability-matrix.v1.json` that also bypasses the
  `max_honest_level` derivation in the adapter layer. The derivation is
  owned by `ADAPTER`; the vendor matrix is its source of truth.
- A change to `engine/crates/membrane-runtime/src/serve.rs` that also
  rewrites the `/federate` route description in `docs/architecture.md` by
  hand. The route is owned by `FEDERATION`; the architecture doc is generated
  by `GENERATION`.
- A change to `AGENTS.md` / `CLAUDE.md` that also redefines a tool name. Tool
  names are owned by `PROTOCOL`; the rules layer is downstream.

### 3.2 What the rule does not do

- It does not freeze the matrix. New rows can be added. The change to add a
  row is itself owned by `RULES` (it changes the rules of the portfolio), and
  the new row must keep the "exactly one owner" invariant.
- It does not prioritize triage over accuracy. If a request is urgent but
  poorly-scoped, the answer is to split it, not to waive the rule.
- It does not allow ad-hoc carve-outs. There is no "this one time" exception.

## 4. Assignment matrix

The matrix is the authoritative contract for layer assignment. Each row is
deterministic. The matrix is intentionally small — it must stay small enough
that a reviewer can verify every request against it in under a minute.

| Kind of feature request | Owner layer | Why this layer and no other |
|---|---|---|
| Add a new MCP tool name | `PROTOCOL` | Tool names are the protocol contract; the live tool list lives in `mcp/server.mjs`. |
| Change an existing MCP tool's input / output schema | `PROTOCOL` | Schema is part of the protocol contract; the live tool definition is the source of truth. |
| Change an MCP tool's behavioral contract (e.g. "scratchpad is ephemeral") | `PROTOCOL` | The contract is documented in `docs/protocol.md` but the runtime enforcement lives in `mcp/server.mjs`. |
| Add a new host adapter | `ADAPTER` | The host registry is `docs/membrane/capability-matrix.v1.json`. |
| Raise / lower a host's `max_honest_level` | `ADAPTER` | The level is derived from the capability matrix; the vendor matrix is the source. |
| Add per-host injection / receipt / gate hooks | `ADAPTER` | The hook taxonomy is owned by the host adapter layer. |
| Change the federation gateway route, concurrency, or deadline | `FEDERATION` | The gateway is the sole route from tools to memory/recall; the loopback `/federate` semantics belong here. |
| Change provider fan-out policy (cancellable, deadline-bound) | `FEDERATION` | The federation layer is the only place that may mutate provider fan-out semantics. |
| Add a new retrieval / memory provider | `ENGINE` | The Crypt engine owns durable memory, retrieval, and embedding work. |
| Change the on-disk schema, SQLite layout, or telemetry envelope | `ENGINE` | The engine is the source of truth for storage format. |
| Add a new embedding model or change the embedding model selection | `ENGINE` | Embedding is a retrieval concern; the engine is the owner. |
| Change the narrative product description, count claims, or positioning prose | `PRODUCT` | Positioning is owned by the product surface; the generated `docs/product.md` carries the source-derived facts. |
| Add a new public surface name (CLI flavor, installer flavor) | `PRODUCT` | Naming is a product-surface decision. |
| Regenerate the generated docs; fix a stale generated artifact | `GENERATION` | `tools/productization/*` is the only place that may regenerate the generated docs. |
| Change the structure of the product-truth gate or the README link inventory | `GENERATION` | The gate and the link inventory are owned by the tool that produces them. |
| Modify `AGENTS.md`, `CLAUDE.md`, or `docs/agent-rules.md` | `RULES` | Workspace rules are the only authority for the rules layer. |
| Add a new workspace-level invariant, forbidden path, or mandatory system | `RULES` | The rules layer is the only place that may mutate the rules of the portfolio. |

A feature request that fits no row above is undefined. The default action is
to **split** the request into per-layer sub-requests, each of which fits one
row. If splitting is impossible, escalate the request as a `RULES`-layer
change that proposes a new row.

## 5. Cross-reference contract

The matrix is consistent with the generated docs and the vendored capability
matrix. The contract is enforced by the cross-reference check in section 6.

- `docs/product.md` is generated from `mcp/server.mjs` tool list and
  `docs/membrane/capability-matrix.v1.json` adapter list. Tool count and
  adapter count claims in `docs/product.md` therefore mirror live source.
- `docs/architecture.md` is generated from the same source. The "Components"
  table is the block-level mirror of the owner-layer taxonomy above: MCP
  server → `PROTOCOL`, client adapters → `ADAPTER`, federation gateway →
  `FEDERATION`, Crypt engine → `ENGINE`, generated docs → `GENERATION`.
- `docs/protocol.md` is generated from the same tool list. The
  "Behavioral contract" bullets are the durable statements `PROTOCOL` must
  uphold.
- `docs/membrane/capability-matrix.v1.json` is the vendor-supplied host
  capability matrix. `ADAPTER` is the only layer that may modify it.

The generated docs intentionally do not contain the assignment matrix itself.
The matrix is **not** regenerated, because it is a rules-layer artifact and
re-generating it from source would create a circular dependency (the rules
layer is not derivable from a file).

## 6. Cross-reference check (doctest)

The matrix in section 4 is correct **only if** the four source-of-truth
artifacts exist and are not stale. The following shell snippet is the
book-gate cross-reference check. It is not a script in the repository; it is
a copy-paste recipe a reviewer can run by hand.

```sh
# 1. The four source-of-truth files must exist.
test -f docs/product.md          || { echo "missing: docs/product.md"; exit 1; }
test -f docs/architecture.md     || { echo "missing: docs/architecture.md"; exit 1; }
test -f docs/protocol.md         || { echo "missing: docs/protocol.md"; exit 1; }
test -f docs/membrane/capability-matrix.v1.json || { echo "missing: capability matrix"; exit 1; }
test -f docs/portfolio-boundaries.md             || { echo "missing: this file"; exit 1; }

# 2. The four generated docs must match live source.
node tools/productization/generate-product-truth.mjs --check

# 3. Every owner layer in section 4 must appear in the generator's source
#    inventory (tools, adapters, components) — i.e. the matrix is not
#    claiming an owner that does not exist in source.
grep -q "MCP server"      docs/architecture.md
grep -q "Client adapters" docs/architecture.md
grep -q "Federation gateway" docs/architecture.md
grep -q "Crypt engine"    docs/architecture.md

# 4. The matrix must not claim ownership of tooling that lives outside the
#    allowedPaths of any task. The tools the owner layer owns are exactly
#    the ones named in section 4: mcp/server.mjs, capability-matrix.v1.json,
#    engine/, tools/productization/, AGENTS.md / docs/agent-rules.md.
```

The recipe is intentionally a manual read-only check. It does not write to
the repository, and it does not run any deferred task command. It is the
shape of the cross-reference check that the book gate will perform against
the matrix; the runtime enforcement belongs to the gate, not to this doc.

## 8. Why this matters

Membrane is a typed product built on a strict source-of-truth hierarchy. When
two layers both claim authority over the same feature, the generator / gate
chain breaks: the generated docs go stale, the README link inventory
diverges, and the trap in MBR-1001 (`README claims six tools but source
exposes nine`) silently returns. The boundary rule is the structural
guarantee that one feature request = one source of truth = one regeneration
flow, and that the book gate can prove it.

The acceptance condition for MBR-1003 — *every feature request can be assigned
to one owner layer without duplicated authority* — is the same condition as
the matrix being non-overlapping and complete. The matrix is non-overlapping
because every row names exactly one `owner`, and every request fits exactly
one row. It is complete because the seven rows cover every file under
`mcp/`, `engine/`, `tools/productization/`, `docs/membrane/`, and the
workspace-rules files.

If a future task extends the matrix, the extension itself is a `RULES`-layer
change and must keep the invariant. If a future task finds a request that
does not fit any row, the answer is to add a row, not to duplicate an owner.
