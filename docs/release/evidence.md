# Release evidence generation (SBOM, provenance, toolchain)

`scripts/release/verify-release-evidence.mjs` and `release/evidence/release-evidence.v1.schema.json` (commit `98233f35`, pre-existing, not modified by MBR-807) already define and enforce the hash-bound `orthic.membrane.release-evidence.v1` manifest shape. This task adds the layer that generates real content for that manifest and binds it to `scripts/release/pipeline/multi-platform-release.mjs`'s (MBR-903) immutable `evidence/releases/<releaseId>/release-generation.json`, instead of duplicating or inventing a second release-identity scheme.

## What this task added

- `scripts/release/evidence/sbom.mjs` — a real SBOM generator. It parses `apps/membrane-hub/pnpm-lock.yaml` and `apps/membrane-hub/src-tauri/Cargo.lock` — the exact JS/TS and Rust dependency graphs compiled into the shipped `membrane-hub` release artifact (`membrane-updater`, the engine's only path dependency of the Tauri binary, depends only on `serde`, already resolved in that same Cargo.lock; nothing else from `engine/Cargo.lock`'s separate, larger crate graph is compiled into `membrane-hub`) — and emits `orthic.membrane.sbom.v1` (`release/evidence/sbom.v1.schema.json`): every `name`/`version`/`source`/`checksum` comes straight from a lockfile line. A component this parser cannot resolve a real checksum for is appended to `gaps`, never given a fabricated hash. Run today against this repository's real lockfiles: 499 resolved components (28 npm + 471 cargo), zero gaps (`scripts/release/evidence/sbom.test.mjs`).
- `scripts/release/evidence/manifest.mjs` — reads one `evidence/releases/<releaseId>/release-generation.json` (MBR-903's output) as the *sole* source of release identity — `tag`, `commit`, `tree`, `release_generation`, per-target sealed-artifact status — and never recomputes a second, parallel `release_generation`. It then generates and writes this task's own real evidence next to it: the SBOM above, plus read-only source provenance (`git show -s --format=...` over the release's own commit — informational only, never a mutating git call) and declared toolchain constraints (`package.json` `engines`/`packageManager`, the hub's Cargo `edition` — never an invoked compiler). `assembleReleaseEvidenceManifest()` is the pure composition step that builds the final `orthic.membrane.release-evidence.v1` object once every required piece is real; the caller runs the pre-existing `verifyReleaseEvidence()` over the result.

## What is a declared gap today, not a fabrication

Running `buildReleaseGenerationEvidence()` against this repository today reports `status: "incomplete"` with named gaps for everything this task is not permitted to produce itself:

- **artifact** — no target in this repository's `release-generation.json` has sealed `status: "verified"` for the current commit without a real macOS/Windows `right-release` build+sign run (MBR-901/MBR-902), which this task's hard rules forbid running.
- **tests** — `release-evidence.v1` requires at least one real test receipt; a full test run was not executed by this task (only its own two new test files were run — see `evidence/productization/MBR-807/commands.log`).
- **signatures** / **platform_trust** — an ed25519 artifact signature and an Apple notarization or Windows Authenticode trust receipt; this task performs no signing.
- **install_receipts** — MBR-806's installed macOS + Windows vector-dispatch receipts; not produced here.
- **event_history** — an explicit `sealed`/`legacy-unsealed` status receipt; not produced here.

None of these are guessed at or filled with a plausible-looking placeholder. `scripts/release/evidence/manifest.test.mjs` proves the full path both ways: (a) against this repository's real, current source identity and real lockfiles, `buildReleaseGenerationEvidence()` binds the exact `release_generation` `computeReleaseGeneration()` (MBR-903's own digest function, imported unmodified) produces for that identity, writes real hash-bound SBOM/provenance/toolchain files, and reports the gaps above; (b) with a synthetic-but-realistic complete set of receipts (the same fixture pattern `verify-release-evidence.test.mjs` already uses), `assembleReleaseEvidenceManifest()` composes a manifest that the pre-existing, unmodified `verifyReleaseEvidence()` accepts (`verified: true`), still keyed to a real `computeReleaseGeneration()` digest rather than a hand-typed hash.

## What still has to happen at the Book 3 final phased gate

Filling in the remaining gaps requires exactly what MBR-903's own acceptance notes already require and this task's hard rules already forbid running here: real `pnpm --dir apps/membrane-hub release:doctor` / `release:build:mac` / `release:build:win` runs (RightKit, MBR-901/MBR-902) on credentialed macOS and Windows machines, a full test run, and MBR-806's installed-acceptance run. Once those exist, `scripts/release/evidence/manifest.mjs`'s CLI (`node scripts/release/evidence/manifest.mjs --release-id ID --target TARGET`) reports what remains, and `assembleReleaseEvidenceManifest()` + `verify-release-evidence.mjs`'s pre-existing verifier bind them into one manifest, per `evidence/releases/README.md`.
