# Source release pipeline

MBR-903 defines a manually invoked, source-only release plan for mac arm64/x64 & Windows x64/arm64. `scripts/release/orchestrate-release.mjs` validates one manifest, then prints JSON; it never builds, signs, notarizes, verifies bytes, uploads, or publishes.

Manifest identity is immutable: `vX.Y.Z` tag, 40-character commit, tree digest, release generation, supported target, artifact SHA-256, evidence SHA-256, `CRYPT_VECTOR_DISPATCH_V2`, and `publish: false`. Ordered stages are provenance → SBOM → sign → platform trust → verify. Each stage carries planned status plus evidence digest. mac targets require `apple-notary`; Windows targets require `windows-authenticode`. Windows arm64 remains conformance-only until an installed receipt promotes it.

Run `node scripts/release/orchestrate-release.mjs --manifest path/to/manifest.json` to print a plan, or add `--validate` for normalized validation output. Platform builders and signing services must produce real receipts before any separate artifact gate; this contract itself is not artifact acceptance.

## Multi-platform orchestration (`scripts/release/pipeline/`)

`orchestrate-release.mjs` above validates one already-populated, per-target manifest. `scripts/release/pipeline/multi-platform-release.mjs` is the layer above it: the actual "manually invoked release command for a tagged source revision" MBR-903's acceptance names, run once per machine, for every target at once. It never builds, signs, notarizes, hardens, uploads, or publishes -- that stays RightKit's job end to end, already wired into `apps/membrane-hub` via `pnpm release:doctor` / `pnpm release:build:mac` / `pnpm release:build:win` (`apps/membrane-hub/right-release.config.mjs`). This layer only:

1. **Resolves source identity, read-only.** `scripts/release/pipeline/identity.mjs`'s `resolveGitSourceIdentity()` runs `git rev-parse HEAD`, `git rev-parse HEAD^{tree}`, and `git status --porcelain` -- informational only, never a mutating git command -- to get the exact commit and tree for the tagged revision.
2. **Computes one deterministic release generation.** `computeReleaseGeneration({ product, vectorDispatch, commit, tree, version, targets })` canonically hashes those inputs (sorted-key JSON, sha256). The same commit, tree, version, and ordered target set always produce the identical digest, on either machine -- this is the literal proof of reproducibility, not an assertion: `node --test scripts/release/pipeline/pipeline.test.mjs` calls it twice with identical inputs and asserts byte-identical output, then changes only `tree` and asserts the digest changes.
3. **Reads what RightKit has already sealed, per platform, without re-implementing verification.** `scripts/release/pipeline/sealed-platforms.mjs` maps each of the four logical targets in `release/contracts/platforms.v1.json` onto the RightKit platform directory that actually produces it (`scripts/release/pipeline/platform-targets.mjs`), then reuses `scripts/release/macos/contract.mjs`'s `sealedReleaseDir` / `readSealedReleaseManifest` / `verifySealedInstallerHash` for mac and `scripts/release/windows/contract.mjs`'s `validateSealedManifest` for Windows -- the exact same MBR-901/MBR-902 functions, never duplicated. `mac-x64` and `windows-arm64` are marked `not-buildable`/conformance-only, honestly, because `apps/membrane-hub/right-release.config.mjs` does not package them today; a target is only ever `verified` when a real sealed `release-manifest.json` exists and its recomputed artifact hash matches.
4. **Fails closed on cross-platform drift.** If a sealed platform manifest's own `commit` field does not match the release's resolved commit -- the exact failure mode of Adrian's real workflow (finish on the Mac, pull to Windows, build there) if the Windows machine builds before pulling, or from a stale branch -- `readSealedPlatformStage` throws `ReleaseDriftError` naming the expected and sealed commits. It is never silently downgraded to "pending": the artifact exists, it is just for the wrong commit.
5. **Writes one immutable, cross-platform record.** `writeImmutableReleaseGeneration` writes `evidence/releases/<releaseId>/release-generation.json` (schema `orthic.membrane.release-generation.v1`, `release/contracts/release-generation.v1.schema.json`), where `releaseId` is `<app>-<version>-<shortcommit>` -- the identical convention `tools/rightkit/packages/release/release-state.mjs`'s `runBuildStateMachine` already uses for `.right-release/sealed/<releaseId>/{mac,windows}/`. Writing the identical plan twice succeeds idempotently (this is what running the command once on the Mac and again after the Windows build, for the same release, looks like: shared fields do not change, only that platform's stage moves from `pending` to `verified`). Writing a *different* plan under the same `releaseId` -- e.g. after `tree` drifted -- throws `ImmutableReleaseConflictError` and never overwrites.

Run `node scripts/release/pipeline/multi-platform-release.mjs --tag vX.Y.Z --version X.Y.Z [--app membrane-hub] [--commit SHA --tree SHA] [--repo-root PATH] [--write]` on each platform's own machine, after that platform's `pnpm release:build:<mac|win>` has sealed its output (or before, to see the plan with that platform still `pending`). Without `--commit`/`--tree` it resolves them from the current `git HEAD`. Without `--write` it only prints the plan; `--write` records the immutable evidence file described above.

## What this does not do

No cargo, pnpm, Tauri, right-release, codesign, notarytool, stapler, spctl, signtool, or AzureSignTool command is ever invoked by anything under `scripts/release/pipeline/`. No CI workflow, GitHub Action, Azure DevOps pipeline, or hosted/self-hosted runner is introduced or required -- per this task's owner override (`MEMBRANE-BOOK-MODE-EXECUTION-RULES.md`, MBR-903/R51), this is local script/orchestration logic only, invoked manually on user-controlled macOS and Windows machines. `scripts/release/verify-release-evidence.mjs` and `release/evidence/release-evidence.v1.schema.json` (pre-existing, not modified here) remain the separate, later evidence-manifest layer (MBR-903's dependent, MBR-807) that binds SBOM/provenance/signature/install receipts per target; `release-generation.json` is what lets that later manifest -- and Adrian, reading two runs by eye -- confirm both platforms' sealed output really is the same exact commit.
